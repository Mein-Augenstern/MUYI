Agent工具设计-写给模型看的接口
====

> 定位：「脚手架设计」系列第 2 篇。[总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md)说脚手架是模型之外的一层，工具是其中"让模型能做事"的部分。本篇只回答一个问题：工具怎么设计，模型才用得好。面试里"工具怎么设计"通常答到"签名加描述加参数 schema"就停了，这一篇往下挖三层：选哪些工具、返回什么、报错怎么写。主线是 Anthropic 的《Writing effective tools for agents》，用 Claude Code 自己的工具做对照。旁通 [结构化输出篇](../agent/结构化输出工程-Pydantic与LLM.md)（下游契约）、[MCP协议与企业落地](../agent/MCP协议与企业落地.md)。

一、换个对象：工具是写给"一个会犹豫的调用方"的
------

传统接口是确定性系统之间的契约：`getWeather("NYC")` 每次都以同样的方式取回纽约的天气。工具不一样，Anthropic 的说法是，它介于确定性系统和非确定性的智能体之间。用户问"今天要带伞吗"，智能体可能调工具，可能凭常识回答，也可能先反问你身在何处，偶尔还会幻觉，或者没弄明白工具怎么用。

所以工具不能再按"给别的开发者封装 API"的思路写。常见的错误是把现有接口逐个包一层，不管智能体用不用得上。要换一个对象来想：调用方的上下文很有限，会误解，会在相近的选项之间犹豫。Anthropic 有个观察：对智能体最"顺手"的工具，人理解起来也出奇地直观。

二、选哪些工具：少而准，把计算推回工具里
------

**工具多不等于结果好。** 通讯录的例子很说明问题：程序可以逐条比对所有联系人，内存又便宜又多；但如果一个工具把全部联系人都返回给模型，让它逐条读下去，就是在用最贵的资源做最笨的事。该做的是 `search_contacts`，而不是 `list_contacts`。

**按工作流合并，而不是按接口拆。** 几个常被串起来调用的接口，合成一个工具：

| 不要这样做 | 这样做 |
|---|---|
| `list_users`、`list_events`、`create_event` | `schedule_event`：找空闲时间并直接排上 |
| `read_logs` | `search_logs`：只返回相关的日志行和一点上下文 |
| `get_customer_by_id`、`list_transactions`、`list_notes` | `get_customer_context`：一次汇齐这个客户的近期信息 |

原则是每个工具目的清晰、彼此不重叠，让智能体像拿到同样资源的人那样拆解任务，同时把原本会占掉上下文的中间输出留在工具内部。工具太多或互相重叠，还会分散它对高效路线的注意力。

**Claude Code 自己就是这么减的。** 文档写明：在 macOS 和 Linux 上，Claude Code 默认不带 `Glob` 和 `Grep` 两个工具，模型改用 Bash 里的 `find` 和 `grep` 来搜。任务清单类工具（`TaskCreate` 等）在较新的模型上也默认不提供，理由是这些工具的定义和提醒本身要占上下文，而新模型不需要一份写出来的清单也能记住多步工作。

**命名要有边界。** 接了几十个 MCP 服务之后，功能相近、目的含糊的工具会让智能体选错。把相关工具归到同一个前缀下（如 `asana_search`、`jira_search`）能划清边界。前缀式还是后缀式，Anthropic 发现对评测结果有不小的影响，但方向因模型而异，所以建议按自己的评测来定。

三、返回什么：高信噪比，并且省着给
------

**只回高信号的信息。** 优先给能直接支撑下一步动作的字段（名称、地址、类型），不要给底层的技术标识（UUID、内部 URL、MIME 类型）。Anthropic 的经验是，把任意的 UUID 换成有语义的名称，甚至只是换成从 0 开始的编号，就能明显减少检索任务里的幻觉。

**让调用方控制详细程度。** 可以给工具加一个 `response_format` 参数，取值"简洁"或"详细"。文档里的 Slack 例子，详细版 206 个 token，简洁版 72 个，只占约三分之一；需要 ID 做后续调用时再要详细版。返回用 JSON 还是 XML 还是 Markdown，没有一定之规，因为模型对不同格式的熟悉程度来自训练数据，同样要靠评测来选。

**给大结果设默认值。** 分页、范围选择、过滤、截断，配上合理的默认参数。Claude Code 的几个上限可以直接参考：

| 场景 | Claude Code 的做法 |
|---|---|
| 工具返回过大 | 工具返回默认限制在 25,000 token；MCP 工具超限的结果存成文件，对话里只留文件路径 |
| Bash 命令输出很长 | 成功的结果内联约 30,000 字符，超出则给出存下来的文件路径加开头 2,000 字符的预览，需要时自己去读 |
| Bash 命令失败 | 内联约 10,000 字符，超出则取头尾各一段，不给文件路径 |
| 按文件名搜索命中太多 | 最多返回 100 个，并带上"结果被截断"的标记，模型据此收窄模式 |

四、报错怎么写：给模型的指路牌
------

截断和报错都不是终点，而是引导模型换一种做法的机会。Anthropic 的建议是：报错要说清楚具体怎么改，而不是丢一个错误码或一段堆栈。

Claude Code 的工具里有几处现成的例子：

* **搜索被拒绝时返回原因。** `Grep` 里写了正则表达式不认的模式，现在会连着 ripgrep 的诊断一起返回，模型据此改正后重搜。文档顺带说了以前的做法：直接报"没找到文件"，哪怕目标文件里明明有要搜的内容。
* **只读到了一部分时说清楚。** `Read` 一次调用默认最多返回 25,000 token；整份文件超出时，它给第一页，并附一条"部分视图"的提示，说明拿到了多少、怎么用参数继续读。
* **读不了的格式给出路。** 遇到 `.xlsx` 这类二进制文件，`Read` 会拒绝，并在报错里建议对应的技能，或者一条能读这个格式的 shell 命令。

OpenAI 的 Codex 团队把这件事推到了架构层面。他们用自定义的 lint 规则守卫代码边界，因为规则是自己写的，报错信息就直接写成修复步骤，随报错一起进入智能体的上下文。

自己写报错时，可以对照这张表：

| 不好的报错 | 好的报错 |
|---|---|
| `Error: invalid parameter` | `date_format 只接受 YYYY-MM-DD，你传的是 "11/6/2024"` |
| `No results found` | `第 2 页之后没有更多结果，共 15 条；可用 status=open 过滤` |
| 一整段调用栈 | 哪个参数、为什么不对、改成什么 |

（表里的三条是本文自拟的示例。）

五、描述就是提示词
------

工具描述和参数定义会进模型的上下文，合在一起就决定了模型会怎么调用。Anthropic 给了一个好用的参照：像给团队新同事介绍这个工具那样写它。你会默认新同事知道的那些背景——专门的查询格式、术语的含义、资源之间的关系——都要写明白。参数名不要有歧义，用 `user_id`，不要用 `user`。

这件事的收益大到出乎意料。文档的说法是，对工具描述做一点精确的修改，就可能带来明显的提升；Claude Sonnet 3.5 在 SWE-bench Verified 上拿到当时的最好成绩，就是在精修了工具描述之后。

**光有 schema 不够，要给例子。** JSON Schema 能约束结构，但说不清用法：可选参数什么时候该给，哪几个参数搭配才有意义，日期该用哪种格式。Tool Use Examples 允许在工具定义里直接放调用示例；Anthropic 的内部测试里，复杂参数处理的准确率从 72% 提高到 90%。建议是每个工具放 1 到 5 个，用真实感的数据，只在对不对不显然的地方放。

**能被搜索到的词要放在前面。** Claude Code 默认开启 MCP 工具搜索，模型是拿任务去匹配工具的名称和描述。所以描述要把关键词写在开头：服务说明和常驻工具的描述超过 4,096 个字符会被截断，经搜索加载的工具描述上限是 16,384 个字符。对比一下两个名字：`search_customer_orders` 一看就知道干什么，`query_db_orders` 则要靠猜。

六、怎么知道改好了：用评测驱动
------

工具设计没有一次写对这回事。Anthropic 的做法是一个循环：先快速搭出原型自己试用，然后建评测，再让智能体帮着改。

* **评测任务要接近真实。** 太简单的沙盒任务考不出问题；好的任务往往要调多次工具，可能多达几十次，比如"给客户 9182 找出重复扣款的相关日志，并判断还有没有别的客户受影响"。每道题配一个可验证的结果，但校验别太严，别因为格式或措辞的差别把对的答案判错。
* **看指标，不只看对错。** 单次工具调用的耗时、调用次数、token 消耗、工具报错数，都值得记。大量重复调用可能说明分页或上限参数不合理；大量参数报错，多半是描述不清楚或者缺例子。
* **让智能体读记录、改工具。** 把评测的原始记录交给模型，让它找出问题、批量修改工具。Anthropic 提到一个真实案例：网页搜索工具上线后，发现 Claude 总是在查询参数里多余地加上年份，带偏了搜索结果，改法就是完善工具描述。
* **留一份没见过的测试集。** 防止工具被改到只适配评测题。Claude Code 的技能评测也是同一个思路：同样的提示，开着技能和关掉技能各跑一遍，比较通过率和 token 开销。

七、追问链
------

* 给模型的工具怎么设计？→ 先换个对象：调用方上下文有限、会犹豫。少而准，按工作流合并，返回高信号的信息，报错写清怎么改，描述当成提示词来写。
* 工具越多越好吗？→ 不是。工具多和互相重叠会分散注意力，定义本身也占上下文。Claude Code 在 macOS 和 Linux 上默认连 `Glob`、`Grep` 都不带，新模型上默认不提供任务清单工具。
* 返回值怎么控制大小？→ 分页、过滤、截断加合理默认值；让调用方选简洁或详细；超限的结果存成文件，对话里只留路径。
* 报错信息重要吗？→ 重要。报错是引导模型换做法的机会：说清哪个参数、为什么不对、改成什么。Claude Code 的 `Grep` 会带回 ripgrep 的诊断，`Read` 会说明只拿到了多少。
* 怎么让模型少调错参数？→ 描述里放 1 到 5 个真实感的调用示例。Anthropic 的内部测试里，复杂参数处理的准确率从 72% 提高到 90%。
* 工具改了怎么知道变好了？→ 用评测：接近真实的任务、可验证的结果、多项指标，再留一份没见过的测试集防过拟合。

一句话总结
------

**工具不是写给开发者的 API 封装，而是写给一个上下文有限、会犹豫的调用方的接口：少而准、按工作流合并、返回高信号的信息、报错直接给出路、描述当成提示词写，最后用评测而不是直觉来判断改没改好。**
