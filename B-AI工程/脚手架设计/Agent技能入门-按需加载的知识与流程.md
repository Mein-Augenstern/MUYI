一、技能是什么：给智能体的一份上岗手册
------

Agent Skills 是一个轻量的开放格式，用来给智能体扩展专门的知识和工作流。规范里的定义很朴素：**一个技能就是一个目录，里面至少有一个 `SKILL.md` 文件**。

```text
deploying-service/
├── SKILL.md          # 必需：元数据加操作说明
├── scripts/          # 可选：可执行的脚本
├── references/       # 可选：参考文档
└── assets/           # 可选：模板等资源
```

`SKILL.md` 的开头是 YAML 元数据，后面是 Markdown 正文。规范定义的元数据一共六个字段，必填的只有两个：

| 字段 | 必填 | 约束 | 作用 |
|---|---|---|---|
| `name` | 是 | 最长 64 个字符；只能用小写字母、数字和连字符 | 技能的名字 |
| `description` | 是 | 1 到 1024 个字符 | 说明它做什么、什么时候用 |
| `license` | 否 | 规范未给长度上限，建议写短 | 许可证的名称，或随技能附带的许可证文件名 |
| `compatibility` | 否 | 最长 500 个字符 | 环境要求；多数技能不需要 |
| `metadata` | 否 | 字符串到字符串的映射 | 给作者自己的工具用 |
| `allowed-tools` | 否 | 空格分隔的工具名 | 预先批准的工具；实验性，各智能体支持程度不同 |

Anthropic 的工程文章给了一个贴切的比喻：写技能就像给新员工准备上岗手册。不必为每个场景单独造一个智能体，谁都能把自己的流程知识写成一份可组合的能力。

一个最小的例子（本文自拟，未实际运行）：

```markdown
---
name: reviewing-pr
description: 审查本仓库的 pull request 时使用。覆盖分层约束、事务边界和日志规范；
  即使用户没有明说"审查"，只要是在看 diff、评估改动风险，也适用。
---

# 审查 pull request

1. 先读 diff 涉及的每个文件的调用方，再判断改动是否安全。
2. 按下面的顺序核对，每项给出"通过 / 不通过 / 不适用"：
   - 分层：Controller 只调 Service，不直接调 Repository
   - 事务：写操作必须在 Service 层的方法上开启事务
   - 日志：不打印手机号、身份证号等个人信息
3. 需要完整规范时，读 `references/conventions.md`。

## 容易漏的地方

- 定时任务的入口没有登录态，取不到当前用户，别按网页请求的写法审查。
```

二、三层加载：目录常驻，正文按需，资料再按需
------

技能之所以能"装很多又不撑爆上下文"，靠的是逐层展开（progressive disclosure）。工程文章的比喻是一本组织良好的手册：先看目录，再翻到具体章节，最后才查附录。规范把它定成三层：

| 层 | 装什么 | 何时进上下文 | 规范给的开销参考 |
|---|---|---|---|
| 元数据 | `name` 和 `description` | 启动时，所有技能的都加载 | 约 100 个 token |
| 指令 | `SKILL.md` 的正文 | 技能被触发时 | 建议不超过 5,000 个 token |
| 资源 | `scripts/`、`references/`、`assets/` 里的文件 | 正文引用到时才加载 | 用到才计 |

客户端实现指南的估计更保守：每个技能给目录增加大约 50 到 100 个 token，装几十个也还紧凑。还有一点常被忽略：脚本被运行时，脚本的代码本身从不进上下文，只有它的输出占 token。所以确定性的操作写成脚本，比让模型现写要省也更稳。

这也解释了规范的两条建议：技能一旦被触发，整份 `SKILL.md` 都会被加载，所以主文件要控制在 500 行以内，详细的参考资料拆到别的文件里。

**"不加载就几乎不花钱"是对的，但不是完全免费。** Claude Code 的文档说得很直白：技能列表里的每一个技能，每一轮都会占一点上下文，不管用没用到。它为此设了预算：技能列表的总量是模型上下文窗口的 1%，超出时从最少被调用的技能开始删描述；`description` 加上 `when_to_use` 的文字，在列表里最多保留 1,536 个字符。所以关键的用途要写在描述的最前面。

三、怎么写：描述决定它会不会被用到
------

编写指南的一句话是整篇的要害：**技能只有被触发才有用**，而描述是触发的主要依据。写窄了，该用的时候不会被用；写宽了，不该用的时候被乱用。模型要从可能上百个技能里挑，靠的就是这段文字。

**描述怎么写。**

* 写清"做什么"和"什么时候用"，并带上用户会说的关键词。
* 用第三人称。描述会被注入系统提示，人称不一致会给识别带来问题。
* 用祈使的口吻，直接告诉智能体什么时候动手："Use this skill when…"，而不是"这个技能会…"。
* 宁可写得主动一些：把适用的场景明确列出来，即使用户没有直接提到这个领域。
* 篇幅保持在几句话到一小段，硬上限是 1024 个字符。

**名字怎么起。** 保持一致的模式，指南推荐动名词形式（动词加 -ing），因为它直接描述这项能力，例如 `processing-pdfs`、`testing-code`。避免含糊的名字（`helper`、`utils`、`tools`）和过于宽泛的名字（`documents`、`data`、`files`）。

**正文怎么写。** `SKILL.md` 应该像手册的目录：给出概览，把细节指向别的文件。具体的尺度：

* **只写模型本来不知道的。** 每一段都问一句：没有这段说明，智能体会做错吗？不会就删掉，拿不准就去测。指南给出的三个检验问题是：真的需要这段解释吗、能不能假定模型已经知道、这一段对得起它的 token 开销吗。
* **引用只深一层。** 参考文件都直接从 `SKILL.md` 链出，不要让模型顺着引用链一层层翻。超过 100 行的参考文件，开头放一份目录，这样模型即使只预览了开头，也知道里面有什么。
* **写清楚什么时候去读哪个文件。**"API 返回非 200 时读 `references/api-errors.md`"，比一句"详见 references 目录"有用得多。
* **把容易踩的坑放在 `SKILL.md` 里。** 指南认为很多技能里最有价值的就是这样一份清单：那些不合常理、不说就会做错的事实。智能体犯了错、你纠正了它，就把这条纠正加进去——这是改进一个技能最直接的办法。
* **简洁的分步说明加一个能跑的例子，往往好过面面俱到的文档。** 复杂的流程给一份清单，让模型抄进回答里逐项打勾。常见的"跑校验器、修错误、再跑"的循环，要明确写出来。

**给多大的自由度，要看任务有多脆。** 编写指南把说明的具体程度分成三档：

| 档位 | 形式 | 适合的情况 |
|---|---|---|
| 高 | 文字说明 | 多种做法都行，取决于上下文 |
| 中 | 伪代码，或带参数的脚本 | 有首选的做法，允许一些变化 |
| 低 | 几乎不带参数的固定脚本 | 操作容易出错，一致性关键，顺序不能变 |

同一个技能里不同的部分可以有不同的档位。

四、什么时候用技能：和 `CLAUDE.md`、钩子、MCP 的分界
------

Claude Code 文档给的创建时机很实用：**同一段说明、清单或多步流程反复往对话里贴，或者 `CLAUDE.md` 里有一节已经从"一条事实"长成了"一套流程"**，就该写成技能。技能的正文只在用到时才加载，所以很长的参考资料在需要之前几乎不占上下文。

各就其位的原则：

| 要放的东西 | 放哪 | 理由 |
|---|---|---|
| 每次会话都该知道的事：编码约定、构建命令、项目结构、"绝不做什么" | `CLAUDE.md` | 常驻；控制在 200 行以内 |
| 偶尔才需要的参考资料（接口文档、风格指南），或用 `/名字` 触发的流程（部署、评审、发布） | 技能 | 按需加载 |
| 每次都必须同样发生、不需要模型思考的事：保存时格式化、拒绝 `rm -rf /` | 钩子 | 由脚手架强制 |
| 该由模型判断怎么执行的步骤，或者内容是知识而不是脚本：发布清单、调试手册 | 技能 | 模型读了再决定 |
| 连接外部系统、拿到可调用的工具 | MCP | 见下一篇 |

两条容易走偏的地方：

* **护栏要放在钩子里。** `CLAUDE.md` 或技能里写一句"绝不编辑 `.env`"只是请求，不是保证；能拦住这次编辑的 `PreToolUse` 钩子才是强制。一条规则必须每次都成立，就把它做成钩子。
* **技能和 MCP 是互补的。** MCP 把智能体连到外部服务，技能扩展它知道的东西，包括怎么把那些服务用好。比如技能可以写上团队的数据库结构和查询习惯。

技能和子代理也能组合：子代理可以在启动时预加载技能，技能也可以用 `context: fork` 在隔离的上下文里运行。

五、加载之后会发生什么
------

这一节是 Claude Code 的具体行为，自己实现技能加载时可以对照。

* **谁触发的。** 默认用户和模型都能触发：用户输入 `/技能名`，模型在觉得相关时自动加载。有副作用或需要控制时机的流程（提交、部署、发消息），应该设 `disable-model-invocation: true`。文档的理由说得很直白：你不会希望模型因为"代码看起来可以了"就自己决定去部署。
* **加载之后一直留着。** 技能被触发时，整份内容作为一条消息进入对话，之后的每一轮都在。所以贯穿整个任务的指导要写成一直有效的指令，而不是一次性的步骤。
* **压缩时有预算。** 对话被压缩后，Claude Code 会把每个技能最近一次的调用重新挂回来，每个保留开头 5,000 个 token，所有技能合计 25,000 个，从最近调用的开始算。重要的东西写在前面。
* **传参和注入。** 参数通过 `$ARGUMENTS` 传进来；`` !`命令` `` 写法会在技能内容发给模型之前执行 shell 命令，把输出填在原位——模型拿到的是真实数据。注入的命令失败时，这次触发整个作废，模型看不到技能内容。
* **预批准的工具只在当轮有效。** `allowed-tools` 列出的工具，在触发技能的那一轮里不用逐个确认，下一条消息发出去就失效，尽管技能内容还留在上下文里。

自己实现客户端时有一条对应的建议：上下文满了要裁剪历史时，把技能内容排除在外。

六、怎么知道它有用：评测
------

平台文档对好技能的定义是：简洁、结构清晰、用真实场景测过。两份指南都强调同一件事：**先建评测，再写大段文档**，这样技能解决的是真实的问题，而不是想象出来的。

* **有没有用，看对照。** 收集几条真实的提示，在全新的会话里各跑两遍——一遍有这个技能，一遍关掉它——比较结果。新会话很重要，因为写技能时留下的上下文会掩盖书面说明的缺口。Claude Code 里可以用 `claude plugin eval`，或者让 skill-creator 插件跑这个循环。
* **会不会被触发，单独测。** 准备 20 条左右的查询，8 到 10 条应该触发，8 到 10 条不应该。最有价值的反例是"近似但不相干"的查询：和技能共享关键词，实际要的是别的东西。模型的行为不确定，每条查询跑几次（3 次是个合理的起点），统计触发率；一条应该触发的查询，触发率过半才算过。
* **从评测出发迭代。** Anthropic 工程文章给的四条准则：从评测开始，先找出智能体在哪些任务上做得不好；为规模而拆分，`SKILL.md` 太长就拆成几个文件；站在模型的角度看它怎么用这个技能，特别注意名字和描述；和模型一起迭代，让它把成功的做法和常犯的错写进技能，走偏时让它自己复盘。
* **安全。** 技能用说明和代码给智能体新能力，也因此有风险：恶意技能可能在环境里埋下漏洞，或者引导智能体外泄数据。只安装来自可信来源的技能，不太可信的先用之前仔细审一遍。

七、它是一个开放标准
------

技能最初由 Anthropic 开发，2025 年 12 月作为开放标准发布。2026 年 10 月，Anthropic 把它捐赠给了 Linux 基金会旗下的 Agentic AI Foundation；公告里说，不加入基金会也照样可以使用标准、参与贡献，标准由来自 Anthropic、Google、OpenAI 等公司的工程师以个人身份维护。捐赠公告给的数字是：已有 70 多个智能体平台接入了 Agent Skills，包括 ChatGPT、Cursor、GitHub Copilot 和 VS Code；累计发布了 100 万个技能，安装近 2.8 亿次。代码采用 Apache 2.0 许可，文档采用 CC-BY-4.0。

对写技能的人，这意味着同一个技能可以在不同的智能体里用，教程里点名的一对是 Claude Code 和 OpenAI Codex。也有两点要留意：

* **规范之外还有各家自己的字段。** 上面提到的 `disable-model-invocation`、`context: fork`、`when_to_use` 都不在开放的规范里，是 Claude Code 的扩展。要跨智能体使用，元数据只用规范的六个字段。
* **数量有上限。** Claude API 每个请求最多带 20 个技能。装的技能多了，每一条元数据都在争抢模型的注意力，所以要挑真正用得上的。

八、追问链
------

* 技能是什么？→ 一个目录，至少有一个 `SKILL.md`，里面是元数据加说明，可以附带脚本和参考资料。它是给智能体的上岗手册。
* 为什么装很多技能也不撑爆上下文？→ 逐层展开：元数据常驻（约 100 个 token），正文触发时才加载，资源引用时才读；脚本的代码不进上下文，只有输出占 token。
* 技能是免费的吗？→ 不完全是。每个技能的元数据每一轮都占上下文。Claude Code 给技能列表的预算是窗口的 1%，描述最多保留 1,536 个字符。
* 描述怎么写？→ 写清做什么和什么时候用，第三人称，祈使口吻，宁可主动一些，不超过 1024 个字符。技能只有被触发才有用。
* 什么该写成技能，什么该写进 `CLAUDE.md`？→ 每次都要知道的写进 `CLAUDE.md`；偶尔才需要的参考资料和用 `/名字` 触发的流程写成技能。
* 什么该做成钩子？→ 每次都必须同样发生、不需要模型思考的事，以及不能有例外的规则。写在提示里只是请求，钩子才是强制。
* 技能和 MCP 什么关系？→ 互补。MCP 给智能体接上外部工具，技能教它怎么把这些工具用好。
* 怎么知道一个技能有没有用？→ 对照评测：同样的提示，有技能和没技能各跑一遍。触发率要单独测，用"近似但不相干"的反例检验描述准不准。

一句话总结
------

**技能是把"按需加载"用在知识上的做法：一份常驻的短描述负责被发现，正文在触发时才进来，资料再按需去读；写得好的关键在描述，用不用得对要靠评测，而它没有例外的规则仍然应该交给钩子。**

面试官视角小结
------

技能这道题，及格线是知道它是按需加载的知识：描述常驻，正文用到才进，所以比把所有规范塞进常驻指令省。往上，面试官多半会拿一个具体场景来问：一段团队规范，该写进常驻指令、做成技能，还是做成钩子？能按"每次都要知道的进常驻指令；偶尔才用的参考资料、按名字触发的流程做成技能；必须每次发生或绝不能发生的做成钩子"来分的，是真用过。再往下问"技能写了不触发怎么办"，答"先改描述，写清做什么、何时用，再上评测看触发率"的，是迭代过技能；只说"把正文写详细一点"的，没抓住关键——决定它会不会被用上的是描述，不是正文。
