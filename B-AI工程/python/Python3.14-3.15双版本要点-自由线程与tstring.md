Python 3.14-3.15 双版本要点：自由线程与模板字符串
====

一句话定位：2026-10 的 Python 处于「**3.15 刚 GA（10 月初）、3.16 进入 alpha（10-13 a1）、3.10 同月末 EOL**」的三事同月节点。真正要沉淀的是 3.14 落地的两大件——**自由线程转正（PEP 779）与模板字符串 t-string（PEP 750）**，3.15 是它们的成熟版。AI 工程师视角：自由线程直接改写推理服务的并发形态，t-string 改写 prompt 拼接的安全边界。

1 版本时间线（2026-10 快照）
------

| 版本 | 状态（2026-10） | 关键事件 |
| ---- | ---- | ---- |
| 3.10 | **2026-10-31 EOL** | 安全补丁停发，存量升级的最后窗口 |
| 3.11 / 3.12 / 3.13 / 3.14 | 维护线 | 2026-10-01 批量发版：3.11.17 / 3.12.15 / 3.13.16（最后一个完整维护版）/ 3.14.8 |
| 3.15 | **GA（2026-10 初，含加映 RC3）** | 当前稳定版 |
| 3.16 | a1（2026-10-13） | 最终版按节奏在 2027-10 |

运维口径：3.10 EOL 是本季度最急的账——扫一遍还在 3.10 的脚本/镜像（很多工具链默认版），迁移目标直接选 3.14+，别停在 3.12 中间态。

2 自由线程：从实验到正式（PEP 779）
------

2.1 三阶段路线
------

- 3.13：实验性自由线程构建（PEP 703 路线，可选独立构建）；
- **3.14：正式支持（PEP 779）**——自由线程不再是"实验构建"而是受支持形态，官方发布计划明确向默认可用演进；
- **3.15：性能成熟**——全局锁移除后的单线程开销持续收窄，多线程扩展性继续抬升。

2.2 工程影响：谁该关心
------

| 场景 | GIL 版本 | 自由线程版 |
| ---- | ---- | ---- |
| CPU 密集多核（推理前处理/批 embedding） | 多进程 + 序列化开销 | 直接 threading，共享内存零拷贝 |
| IO 密集（高并发调用 LLM API） | asyncio 已够用 | 收益有限，别为它迁移 |
| C 扩展重仓（numpy/torch 老版本） | 兼容稳 | 依赖链自由线程支持是否跟进（主流库 3.14 起已跟进） |

追问链预判："GIL 没了，线程安全怎么办"→ GIL 从来不是线程安全的保证，只是把竞态窗口藏起来；自由线程下 `dict`/`list` 等内建类型保证内部一致性，但业务级不变式仍要锁——这点答不清的人，多半也没写对过多线程 Java。

3 模板字符串 t-string（PEP 750，3.14 落地）
------

```python
from string.templatelib import Template
t = t"给 {user} 的额度是 {amount}"
# t 不是 str——是 Template 对象：静态文本与插值分离
```

- 与 f-string 的本质差：f-string 即时求值拼死字符串；t-string **延迟渲染**，把"结构"交给库处理——HTML 自动转义、SQL 参数化、**prompt 组装时对用户输入做隔离**；
- 安全叙事：这是把"注入类漏洞"从开发者手上移到库层的老思路（同 SQL 参数化），prompt 工程里对应"用户内容与系统指令的结构性隔离"；
- 生态跟进：Web 框架的转义渲染陆续原生支持；迁移策略——新代码 prompt/SQL/HTML 拼接处优先 t-string，存量 f-string 不必动。

4 其余值得记的（3.14 起稳定）
------

- **延迟求值注解**（PEP 649/749）：`from __future__ import annotations` 转正——大库（pydantic/fastapi 生态）的类型解析更稳更快；
- 3.16 方向预告：alpha 期特性未定稿，只跟节奏不写结论。

面试一句话收口：Python 用两次大版本把"并发"和"拼接安全"这两个最老的长尾问题各补了一个官方答案——自由线程与 t-string，都能对应到你自己的服务里哪一段代码受益，这题就赢了。
