智能体工程面试题-上下文与脚手架
====

看在前面
------

B 轨面试题的进阶篇，接[基础篇](LLM应用面试题合集.md)的 Q1–Q20，从 Q21 起共 24 题。基础篇的八主题在 2025 年之前够用；之后面试往两个方向深挖了：一是循环里的上下文（膨胀、分层、记忆、缓存），二是模型之外的那一层（脚手架、验证、人机协同）。

答法和基础篇相同：**先结论、再机制、最后给一个具体的做法或数字**。区别在素材：基础篇的例子来自 ai-service 的生产代码，这一篇的例子来自 Claude Code、Anthropic、OpenAI 的公开资料，属于学习整理。"我们生产上是……"这一句，要换成你自己的项目。

九、循环里的上下文
------

**Q21 · 窗口都到 100 万了，还需要做上下文工程吗？**

答：需要，但问题变了。窗口够大、又会自动压缩之后，"塞不塞得下"不再是主要矛盾，剩下两件事：钱——每个请求都把整段上下文重发一遍；注意力——东西太多本身是噪音，技能触发不准，约定也会被忘。所以问题从"怎么塞得下"变成了"什么时候让模型看到什么"。深入：[上下文分层篇](../上下文工程/Agent上下文分层-常驻按需与工具太多怎么办.md)、[总览篇](../上下文工程/上下文工程总览-窗口里该放什么.md)。

**Q22 · Agent 跑久了上下文膨胀，怎么治？**

答：先记账再动手：系统提示、工具定义、历史、检索片段各占多少，用户开口之前窗口已经被占了百分之几。然后四种手段各有适用面：数据装不下，用按需检索，窗口里只放文件路径、链接这类标识符，用到再取；要维持对话流，用压缩，旧轮折成摘要，最先清的是历史深处的工具原始结果；有清晰的里程碑，用结构化笔记，写到窗口外，需要时读回；可以并行的探索，交给子代理，只把摘要带回来。Claude Code 是混着用的。深入：[四板斧篇](../上下文工程/Agent上下文工程-注意力预算与四板斧.md)。

**Q23 · 工具太多，模型总选错、填错参数怎么办？**

答：三步。先裁，最常用的三到五个保持常驻；再合并语义重叠的；多到一定程度，上工具搜索——工具定义延迟加载，模型先搜，搜到的才展开完整定义。Anthropic 的例子里，上下文占用从约 77K 降到约 8.7K，少了 85%，准确率反而上升，而且不破坏提示缓存。深入：[上下文分层篇](../上下文工程/Agent上下文分层-常驻按需与工具太多怎么办.md)、[工具设计篇](../脚手架设计/Agent工具设计-写给模型看的接口.md)。

**Q24 · 常驻指令写多长合适？越详细越好吗？**

答：只写模型自己查不到的。读代码能发现的、它自己会去查的，都不要写；该写的是仓库里没有的决定、看起来没用其实还在用的目录、纠正过两次的事。控制在 200 行以内，每一行都具体到可以验证。想拆小就用按需加载，用 `@` 导入等于没拆。深入：[上下文分层篇](../上下文工程/Agent上下文分层-常驻按需与工具太多怎么办.md)。

十、记忆
------

**Q25 · Agent 的记忆是什么？和 checkpoint、RAG 是什么关系？**

答：记忆是从经验里得到、跨会话保留、之后能读回的内容。checkpointer 是会话状态的持久化，用来断点续跑，不产生新知识——那是存档，记忆是学习。RAG 只有读取侧，没有"从交互中积累"的写入侧，它是记忆的一种手段，不是记忆本身。深入：[记忆系统篇](../上下文工程/Agent记忆系统-从会话状态到跨会话记忆.md)、[ReAct 篇](../agent/ReAct与LangGraph工程实践.md)。

**Q26 · 记忆系统怎么落地？一定要上框架吗？**

答：不一定。最小形态用文件系统就够：会话内按主题写笔记，关键事实逐字引用；会话开始时只把索引注入窗口，正文按需读；空闲期拿会话日志当依据整理，去重、纠错、补链接。指引用途比规定步骤有效——Anthropic 的实验里，规定"只记失败"反而让模型丢掉大部分收益。要多个智能体共享记忆，或者检索本身很复杂，再考虑 Letta、Mem0 这类方案。深入：[记忆系统篇](../上下文工程/Agent记忆系统-从会话状态到跨会话记忆.md)。

**Q27 · 记忆出错了怎么办？**

答：错误记忆比没有记忆更糟，它带着"自己写的"信任光环。Anthropic 的实验里，一条记错的位置让 Claude 在同一个地方绕了三次，最后主动放弃。治理靠三件事：有可校验的依据（会话日志、原始文档），空闲期定期整理纠错，给记忆留删除出口。另外，易变的信息不进长期记忆。深入：[记忆系统篇](../上下文工程/Agent记忆系统-从会话状态到跨会话记忆.md)。

十一、提示词缓存
------

**Q28 · 提示词缓存是什么？为什么能便宜？**

答：模型处理输入时算出的中间状态可以被留下来：下一个请求的开头和上次一样，就直接复用，不再重算。读取价大约是输入价的十分之一，个别模型更低；写入要加价，Anthropic 的 5 分钟档是 1.25 倍，读一次就回本。对智能体格外重要，因为每一轮都在重发全部历史。深入：[提示词缓存篇](../上下文工程/提示词缓存-让重复的上下文变便宜.md)。

**Q29 · 什么会打断缓存？上下文该怎么排？**

答：它只认开头，而且要一字不差：前缀里任何一处变了，后面全部重算。最常见的打断是中途改工具定义、系统提示里放时间戳、改写历史而不是追加、中途换模型。所以顺序是少变的在前：系统提示和工具、项目指令、会话上下文、对话消息；要更新的信息用消息传，不改前面的内容。深入：[提示词缓存篇](../上下文工程/提示词缓存-让重复的上下文变便宜.md)、[上下文分层篇](../上下文工程/Agent上下文分层-常驻按需与工具太多怎么办.md)。

**Q30 · 怎么知道缓存命中了？命中率低怎么查？**

答：看用量字段，别猜。Anthropic 给的是读取、写入、断点后输入三个数，加起来才是总输入；写入一轮接一轮都很高，说明前缀里有东西在变。再用诊断工具定位：传入上一个响应的 id，API 会告诉你是模型、系统提示、工具还是消息历史分了叉。深入：[提示词缓存篇](../上下文工程/提示词缓存-让重复的上下文变便宜.md)。

**Q31 · 缓存能代替上下文工程吗？**

答：不能。命中的 token 仍然在窗口里，仍然占注意力，缓存只改变价格和等待时间。缓存解决的是"重复的太贵"，不解决"内容太多"，该裁的还是要裁。深入：[提示词缓存篇](../上下文工程/提示词缓存-让重复的上下文变便宜.md)、[四板斧篇](../上下文工程/Agent上下文工程-注意力预算与四板斧.md)。

十二、脚手架
------

**Q32 · 同一个模型，为什么 Claude Code 好用，自己做的不行？**

答：差别在模型外面那一层脚手架：它管模型看到什么、能做什么、谁确认做完、什么不能做，基本形状是"收集上下文、行动、验证"的循环。自己拼的最容易省掉验证——没有一个能跑出通过或失败的检查，模型说"做完了"就是它的全部依据。深入：[脚手架总览篇](../脚手架设计/Agent脚手架总览-ClaudeCode好用在模型之外.md)、[复刻清单](../脚手架设计/Agent脚手架复刻清单与面试追问.md)。

**Q33 · 规则写在提示词里，还是做成钩子？**

答：分两种指令。让模型决定的，用提示词，大多数属于这一类；必须每次发生或绝不能发生的，用钩子或拒绝规则，由脚手架强制。判断方法：一行规则反复加"重要"还是被忽略，就该做成钩子；为一些只是偏好之类的事写了钩子，就该删掉。深入：[脚手架总览篇](../脚手架设计/Agent脚手架总览-ClaudeCode好用在模型之外.md)。

**Q34 · 智能体说做完了，怎么知道它真做完了？**

答：给它一个能跑出通过或失败的检查，最关键的那条做成硬门禁（Stop 钩子），而不是写在提示词里盼它遵守；只认证据，不认结论。检查本身也要守得住：规则文件取自主干，评审绑定到具体的提交，智能体改不了对自己有利的判据。深入：[验证回路篇](../脚手架设计/Agent验证回路-让智能体自己发现错了.md)。

**Q35 · 长任务跨好几个上下文窗口，怎么不跑偏？**

答：把状态放到窗口外面：进度文件、一份全部标成未通过的功能清单、每次收工就提交。节奏上一次只做一个功能，做完才把清单翻过来；每个新窗口开场先认路再动手。被追问要不要多智能体：先把单个智能体的进度状态和验证回路做扎实，团队会增加协调开销和 token 消耗。深入：[长任务篇](../脚手架设计/Agent长任务-进度状态与增量交付.md)。

**Q36 · 一段团队规范，该写进常驻指令、做成技能，还是做成钩子？**

答：每次都要知道的，进常驻指令；偶尔才用的参考资料、按名字触发的流程，做成技能——描述常驻，正文用到才进；必须每次发生或绝不能发生的，做成钩子。技能写了不触发，先改描述，写清做什么、何时用，再上评测看触发率。深入：[技能入门篇](../脚手架设计/Agent技能入门-按需加载的知识与流程.md)。

**Q37 · MCP 和 function calling 是什么关系？MCP 解决了什么，没解决什么？**

答：先分层次：function calling 在推理层，管模型会不会用工具、怎么调；MCP 在接入层，管工具从哪来、怎么安全地接进来。两者是上下层，不是竞争关系。MCP 解决的是接入的标准化：工具、资源、提示词三种原语，stdio 和 Streamable HTTP 两种传输，基于 OAuth 2.1 的授权。没解决的是安全和成本：注解只是给模型看的提示，不能当权限用；规范自己声明无法在协议层面强制安全；工具接多了，常驻的定义先把上下文吃掉。深入：[MCP 企业落地篇](../agent/MCP协议与企业落地.md)、[MCP 入门篇](../脚手架设计/MCP协议入门-原理、安全与第一个Server.md)。

十三、人机协同
------

**Q38 · 确认框弹个不停，怎么治？**

答：先承认审批是有成本的：问得越多，人越会不看就点，最后等于没问。把"每个动作问一次"改成"计划确认一次，边界内不打扰"；划清风险象限，先写出永不自动放行的清单；拿不准的操作交给一个只看事实、没看过模型推理的审查者。不可逆的、跨信任边界的，无论如何问人。深入：[人机协同篇](../agent/Agent人机协同-从头部智能体看审批与权限设计.md)。

**Q39 · 自动审批能替代人吗？**

答：不能。公开的数据是"过于主动"的动作上漏报 17%，多数漏报是误判了用户是否同意。它的定位是替代"跳过权限"这种偷懒做法，不是替代高危场景下的人工审查。深入：[人机协同篇](../agent/Agent人机协同-从头部智能体看审批与权限设计.md)。

**Q40 · 动作被拦截之后，智能体该怎么办？**

答：拒绝并带上理由，让模型换一条更安全的路继续；连续被拒达到阈值（3 次连续或 20 次累计）再升级给人。直接卡死会把误拦变成致命问题。深入：[人机协同篇](../agent/Agent人机协同-从头部智能体看审批与权限设计.md)。

十四、评测与成本
------

**Q41 · Agent 怎么评测？和单测有什么不同？**

答：单测是输入确定、输出确定；agent 三样都不确定：输出是自然语言，路径每次不一样，执行还会改环境。所以第一原则是别评输出文本，评"任务有没有完成"，用端到端的判定器。三层从便宜到贵：单步、轨迹、端到端，分别对应每次改提示词、每日或每周回归、发布前。深入：[评测篇](../agent/Agent评测与可观测-guards与成本.md)。

**Q42 · 让模型当裁判靠谱吗？**

答：要先校准。拿人工标注的样本验证裁判的准确率，Anthropic 的经验是先拿 50 个；裁判不准，整个评测体系就是沙上城堡，不达标就换成代码判定器。验证回路那边的结论相同：明确的规则最可靠，模型裁判只作补充。深入：[评测篇](../agent/Agent评测与可观测-guards与成本.md)、[验证回路篇](../脚手架设计/Agent验证回路-让智能体自己发现错了.md)。

**Q43 · Agent 上线后怎么观测？出了事故怎么排障？**

答：每一轮的模型输入输出、工具调用和结果、耗时、token 数都要结构化落盘，能重放一条完整的决策链——这是线上排障的唯一依据。盯三个指标：任务完成率、平均轮数（步数失控的信号）、单任务 token 成本（预算失控的信号）。没有轨迹落盘的智能体，出了事故就是黑盒。深入：[评测篇](../agent/Agent评测与可观测-guards与成本.md)。

**Q44 · Agent 的 token 成本怎么控？**

答：四个手段一起上：工具结果进历史之前先摘要或截断；历史裁剪和压缩；便宜的模型跑分类和路由；轮数上限。再让每轮重发的历史里不变的前缀命中提示词缓存。最大的隐性成本是步数失控。深入：[评测篇](../agent/Agent评测与可观测-guards与成本.md)、[四板斧篇](../上下文工程/Agent上下文工程-注意力预算与四板斧.md)、[提示词缓存篇](../上下文工程/提示词缓存-让重复的上下文变便宜.md)。

面试官视角小结
------

1. **开场先给框架**：上下文这组题，先说"放什么、何时放、留多久、多少钱"四个维度，再落到被问的那一个；脚手架这组题，先说"模型之外的那一层管四件事"，再展开。有框架的答案和只有碎点的答案，半分钟内就分得出来。
2. **每题带一个数字或一个反例**：工具搜索少了 85%；一条记错的位置让模型绕了三次；自动审批漏报 17%；裁判先用 50 个样本校准。数字说明读过一手资料，反例说明知道东西会在哪里坏。
3. **三组最容易混的概念要主动分清**：记忆和会话状态持久化，缓存和上下文工程，让模型决定和由脚手架强制。主动分清的，是理解了；被追问才分的，是背了名词。
4. **答不上的题，回到原则**：窗口是预算、注意力有限、每一轮都在为全部上下文付费、模型的输出是概率性的——这四句能推出这一篇的大多数答案。
