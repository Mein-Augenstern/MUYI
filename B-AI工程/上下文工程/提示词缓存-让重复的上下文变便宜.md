一、为什么智能体离不开它
------

Claude Code 的文档把原理说得很直白：每发一条消息都是一次新的 API 请求，模型不记得上一轮，所以脚手架把系统提示、项目上下文、之前的每条消息和工具结果，连同新消息，全部重发一遍。新内容追加在末尾，所以每次请求的大部分和上一次完全相同。提示词缓存做的，就是让 API 不去重新处理没变的那部分。

Claude Code 团队的说法更进一步：像 Claude Code 这样长时间运行的智能体产品，是靠提示词缓存才做得成的，它让后面的往返可以复用之前的计算，明显降低延迟和成本。他们把整个脚手架围绕提示词缓存来搭，并且给缓存命中率配了告警——命中率太低，按线上事故处理。

接回[四板斧篇](Agent上下文工程-注意力预算与四板斧.md)：循环里每一轮都全量重建上下文，历史每轮重发，长轨迹是平方级的 token 压力。缓存没有消灭这笔账，它做的是把"重复的那部分"的单价降到原来的十分之一左右，个别模型更低。

二、原理：只认开头，而且要一字不差
------

**缓存的是计算结果，不是文本。** 模型处理输入时要算出中间状态（键值状态，KV），后面的 token 靠它回看前面的内容。提示词缓存把这段状态留下来：下一个请求的开头和上次一样，就直接复用，不再重算。OpenAI 的说法是，提示词缓存保存的是 KV 张量，不是 token 本身。

**只认前缀，而且是精确匹配。** Anthropic 的要求是 100% 相同，文字和图片都算。Claude Code 的文档强调了两点：前缀里任何一处变了，它后面的内容全部重算；没有按文件、按片段的缓存。这和平时理解的缓存不一样——不是"这一块没改就还能用"，而是"从开头到这里每一个字节都没改，才能用"。

**前缀的顺序是固定的。** Anthropic 的缓存范围依次是工具定义、系统提示、消息，三层依次叠加。前面一层变了，后面全部失效：改一个工具的定义，整段作废；只动消息，前面的工具和系统提示仍然有效。

```text
第 1 轮  工具 | 系统提示 | 指令 | 消息1
         → 首次：全价计算，并写入缓存
第 2 轮  工具 | 系统提示 | 指令 | 消息1 | 消息2
         → 前一段命中，只算消息2
第 3 轮  工具 | 系统提示 | 指令 | 消息1 | 消息2 | 消息3
         → 前两段命中，只算消息3
出事     工具 | 系统提示 | 指令 | 消息1 | 消息2 | 消息3
         → 工具定义变了：从头重算
```

**缓存不改变模型的输出。** Anthropic 和 OpenAI 都写明，提示词缓存不影响输出生成，回答和不用缓存时一样。它改变的只有价格和等待时间。OpenAI 特意补了一句：这不代表同样的请求会得到逐字相同的回答，采样本来就有随机性。

还有两点让人放心：缓存按组织隔离，不同组织即使提示词完全相同也互不可见；也没有手动清空缓存的办法，条目到期自动消失。

三、各家怎么做
------

先看怎么开启、门槛多高、能活多久：

| | 怎么开启 | 最短长度 | 有效期 |
|---|---|---|---|
| Anthropic | 需要标记：请求顶层加一个 `cache_control`（自动缓存），或在具体内容块上标记（手动断点） | 按模型分四档：512、1,024、2,048、4,096 token | 默认 5 分钟，每次使用免费刷新；可选 1 小时 |
| OpenAI | 默认开启 | GPT-5.6 及以后是 1,024 token；更早的模型随请求设置变化 | GPT-5.6 及以后：默认最短 30 分钟，可选 12 小时；更早的模型 `in_memory` 约 5–10 分钟、最长 1 小时 |
| Gemini | 默认开启（隐式缓存，Gemini 2.5 及以后的模型）；显式缓存只支持 Gemini 3 和 2.5 | 4,096（Gemini 4 和 3.x）或 2,048（2.5 系列）token | 隐式缓存的有效期文档未写明 |
| DeepSeek | 默认开启，不用改代码 | 文档未写 | 不用时自动清理，通常几小时到几天 |

两个容易踩的细节：

* **不到最短长度，不缓存，也不报错。** Anthropic 的提示是看用量字段：写入和读取两个数都是 0，多半就是没够长度。
* **有效期从请求开始时算，不是结束时。** Anthropic 的 5 分钟里包含生成回复的时间：一次回复流式输出了 4 分钟，下一个请求要在它结束后的约 1 分钟内发出，才能用上。

再看价格。下表的倍数都是相对该模型的普通输入价：

| | 写入缓存 | 读取缓存 | 备注 |
|---|---|---|---|
| Anthropic | 5 分钟档 1.25 倍；1 小时档 2 倍 | 0.1 倍；部分新模型是 0.025 或 0.05 倍 | 例：Claude Opus 5.5 输入 $4，5 分钟写入 $5，1 小时写入 $8，读取 $0.20（每百万 token） |
| OpenAI | GPT-5.6 及以后：30 分钟档 1.25 倍，12 小时档 2.5 倍；更早的模型写入不另收费 | 多数模型 0.1 倍，四个型号 0.05 倍 | 写入价是这批 token 的单价，不是在输入价上再加一笔 |
| Gemini | 定价页没有单独的写入价 | 约为输入价的十分之一，Gemini 4 系列是二十分之一（推算） | 例：Gemini 2.5 Pro 输入 $1.25，缓存 $0.125 |
| DeepSeek | 定价页没有单独的写入价 | deepseek-flash：命中 $0.006，未命中 $0.3，约为五十分之一（高峰时段，推算） | 尽力而为，不保证命中率 |

自托管推理时，对应的是 vLLM 的自动前缀缓存（Automatic Prefix Caching）：把之前请求算过的 KV 缓存留下来，新请求的开头一样就复用。它按块匹配，有一个 token 不同，那一块和后面的块都要重算。它省的是算力，而且只缩短预填充，不缩短生成。跨轮复用的条件和上面各家一样：之前的消息逐 token 不变，新内容追加在末尾。显存怎么算，见[推理与部署篇](../推理与部署/自托管LLM推理-vLLM与SGLang.md)。

四、一笔账：什么时候回本
------

写入要加价，所以缓存不是白给的。OpenAI 文档算过一笔账（按 0.1 倍读取、1.25 倍写入）：一段前缀写一次、完整复用一次，总共花掉 1.35 倍的输入价；不用缓存的话，处理两遍是 2 倍。十次请求里写一次、读九次，总共 2.15 倍；不用缓存是 10 倍。

Anthropic 定价页的结论相同：5 分钟档读一次就回本，1 小时档要读两次。按倍率验算（推算）：5 分钟档是 1.25 + 0.1 = 1.35，低于处理两遍的 2；1 小时档读一次是 2 + 0.1 = 2.1，还高于 2，读两次是 2.2，低于 3。

所以要不要开，不取决于技术，取决于两件事：这段前缀会不会被重复使用，以及两次使用之间隔多久。

五、什么会打断缓存
------

| 动作 | 为什么会打断 | 怎么避免 |
|---|---|---|
| 系统提示里放了时间戳、请求 ID | 每个请求的系统提示都不一样，前缀从第一块就对不上 | 系统提示写成常量，每次都变的东西放进消息。Claude Code 团队承认踩过这个坑 |
| 中途增删工具、调整顺序、改参数 | 工具定义排在最前面，一变后面全失效。Claude Code 团队说，这是人们弄坏缓存最常见的方式 | 会话中途不动工具集；确实要加，交给子代理，或用支持中途加工具的方式 |
| 工具定义序列化不稳定 | 内容没变，但 JSON 键的顺序每次不同（Swift、Go 等语言会打乱） | 固定序列化顺序，比如键排序 |
| 改写了历史消息，而不是追加 | 之前的内容变了，前缀对不上 | 历史只追加；模型的回复和工具结果原样回传 |
| 压缩、摘要、截断 | 新的历史和旧的没有共同前缀 | 把压缩放在任务的间隙；压缩请求本身复用父对话的前缀（见下一节） |
| 中途换模型 | 每个模型有自己的缓存，内容相同也得重算 | 会话开始时就定好模型；要换，让子代理去办 |
| 中途改推理强度、开关快速模式 | 这些设置会被渲染进前缀；多数模型上每个推理强度各有一份缓存 | 同上；支持的模型可以用"配置更新"来改，不动前面的内容 |
| 两次请求隔得太久 | 缓存过期 | 用 1 小时档；或在用户到来之前先预热 |
| 前缀太短 | 不到最短长度，不缓存 | 看用量字段确认；差一点的话，适当补足反而划算 |
| 网关把缓存标记丢了 | 请求照样成功，但整段历史每一轮都按原价计费 | 确认网关原样转发 `cache_control`，再用用量字段核对 |
| 清理旧的工具结果 | 改动了历史 | 一次清够本（Anthropic 的参数是 `clear_at_least`），不要一点一点清 |

最后一行的道理是：每清一次，缓存就要重建一次，重建就要再付一次写入价。

六、为缓存安排上下文
------

**少变的在前，易变的在后。** Claude Code 的排法是四层：静态的系统提示和工具、项目指令文件、会话上下文、对话消息。越靠前的层，能共享它的请求越多——系统提示是所有会话共用，项目指令是同一个仓库共用，对话只有它自己用。两家的官方建议都是这一句：稳定的内容放开头，时间戳和与用户相关的内容放末尾，或者挪进后面的消息。

**要更新的信息，用消息传，不改前面。** Claude Code 团队的做法是在下一条用户消息或工具结果里加一段系统提醒，带上更新后的信息。计划模式和技能加载也是把指令作为对话消息追加的，所以不碰已经缓存的前缀。Anthropic 在新一些的模型上支持同样的思路：把新的系统指令作为一条 `role: "system"` 的消息追加到对话里，而不是改顶层的系统提示字段。

**压缩也有省钱的写法。** 压缩要先把整段对话发给模型去写摘要。最省事的做法是另发一个请求，换一套系统提示、不带工具——这恰好是花钱的陷阱：前缀从第一个 token 就对不上，缓存一点用不上。Claude Code 的做法是：压缩请求沿用父对话完全相同的系统提示、上下文和工具定义，把父对话的消息放在前面，把"请总结"作为一条新的用户消息追加在末尾。这样压缩请求本身几乎全部命中缓存，新增的只有那一句总结指令。

**变化快慢不同的段，分开打断点。** Anthropic 允许最多 4 个断点。官方的例子是把工具定义、稳定指令、知识库文档、对话历史分别断开：知识库文档每天更新，更新时前两段照样命中。断点要打在"跨请求保持不变的最后一块"上；打在每次都变的内容上（比如带时间戳的那一块），就会每次都写入、一次也读不到。对话增长时，只要每轮新增的内容少于 20 块，把断点放在最后一块就够了。

**并发要排个先后。** Anthropic 的缓存条目要等第一个响应开始之后才可读。需要并发的请求都命中，就先等第一个响应开始，再发后面的。Claude Code 在并行派出同前缀的智能体时，默认把第一个之外的请求扣住最多 5 秒，就是在等这个。

**子代理是冷启动，fork 不是。** 子代理有自己的系统提示和工具，第一次请求读不到父对话的缓存，要在自己的几轮里重新暖起来；fork 完整继承父对话的系统提示、工具和历史，第一次请求就能命中。

**可以预热。** Anthropic 支持发一个 `max_tokens: 0` 的请求，把系统提示和工具定义先写进缓存，用户的第一句话就不用等这段计算；这次请求按写入价计费。OpenAI 在 Responses API 里有对应的 `prompt_cache_options.prewarm` 开关。

**工具太多，用延迟加载。** Anthropic 的 `defer_loading` 把一部分工具的定义放在前缀之外，模型通过搜索发现它时，定义才作为一段引用追加到对话里，前缀原样不动。Claude Code 在支持的模型上默认这样处理 MCP 工具，所以会话中途有 MCP 服务连上或断开，已经缓存的内容不受影响。详见[上下文分层篇](Agent上下文分层-常驻按需与工具太多怎么办.md)。

七、怎么知道命中了：看用量字段，别猜
------

Anthropic 的响应里有三个输入字段，加起来才是总输入：

| 字段 | 含义 |
|---|---|
| `cache_read_input_tokens` | 这次请求从缓存里读到的 token |
| `cache_creation_input_tokens` | 这次请求写入缓存的 token |
| `input_tokens` | 既没读也没写的那部分，也就是最后一个断点之后的内容 |

注意 `input_tokens` 不是全部输入，只是断点后面的一小段。按它估上下文长度会严重偏低。

```python
def cache_stats(usage: dict) -> dict:
    """从 Anthropic 风格的 usage 里算总输入、命中率、写入占比。"""
    read = usage.get("cache_read_input_tokens", 0)
    write = usage.get("cache_creation_input_tokens", 0)
    plain = usage.get("input_tokens", 0)  # 只含最后一个断点之后的 token
    total = read + write + plain
    return {
        "total_input": total,
        "hit_rate": round(read / total, 3) if total else 0.0,
        "write_ratio": round(write / total, 3) if total else 0.0,
    }
```

其他几家对应的字段：OpenAI 是 `usage.input_tokens_details.cached_tokens` 和 `cache_write_tokens`，官方定义的命中率是"命中的 token ÷ 总输入 token"，建议按用户、工作区或天分组统计；DeepSeek 是 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`；vLLM 暴露两个 Prometheus 计数器，`vllm:prefix_cache_hits` 和 `vllm:prefix_cache_queries`。

Claude Code 里可以直接看：状态栏读得到每轮的两个数，`/usage` 给出整个会话的汇总。文档里的示例是"91% of input tokens from cache"。它给的经验法则是：读取远多于写入，说明缓存在起作用；写入一轮接一轮都很高，说明前缀里有东西在变。

光看数字只知道"没命中"，不知道为什么。两家的诊断工具补的就是这一块：Anthropic 的缓存诊断让你传入上一个响应的 `id`，API 会比较前后两个请求，指出是在模型、系统提示、工具还是消息历史上分了叉，并给出原因代码，比如 `system_changed`（通常是系统提示里拼了时间戳）和 `tools_changed`（工具有增删、顺序变了，或者 schema 序列化不稳定）。OpenAI 提供命中率面板和诊断工具。

排查顺序可以这样走（这一条是本文的归纳）：

1. 写入和读取都是 0：没够最短长度，或者标记在半路被网关丢了；
2. 请求没变但读取是 0：缓存过期了，或者前缀太短；
3. 写入每一轮都很高：前缀在变，用诊断工具找分叉点。

八、缓存不替你省上下文
------

**命中的 token 仍然在窗口里，仍然占注意力。** Gemini 的说法是，模型不区分缓存的 token 和普通输入 token，缓存内容就是提示词的前缀。窗口越长、召回越差这件事，不会因为缓存而改变。缓存解决的是"重复的内容太贵"，不解决"内容太多"——该裁的还是要裁，见[四板斧篇](Agent上下文工程-注意力预算与四板斧.md)。

**命中率没有保证。** OpenAI 写明，最短有效期只决定是否有资格按缓存价计费，不保证每个请求都能复用；DeepSeek 说自己是尽力而为；Gemini 的隐式缓存也不承诺省钱。

**限流各家算法不同。** OpenAI 的缓存 token 仍然计入每分钟 token 限额；Anthropic 的缓存命中不占限流额度。

**长会话不会因为缓存而便宜到可以忽略。** Claude Code 的文档提醒：一个开了一整天的会话里问一句话，仍然要按整段对话计费，只是按缓存价。

**1 小时档不是白给的。** 它适合两次使用之间会隔超过 5 分钟的场景；如果每次都是连续几分钟的短促使用，更高的写入价付了，更长的有效期却用不上。

九、和 KV cache 是什么关系
------

两个词经常混着说。KV cache 是推理时每个请求的中间状态，占的是显存，PagedAttention 这类技术管的是它怎么摆放、怎么复用。提示词缓存是把这部分状态跨请求留下来，并按优惠价计费；落到推理引擎上，就是 vLLM 的自动前缀缓存。前者是服务端的事，后者才和写智能体的人有关：你决定不了 KV cache 怎么调度，但前缀怎么排、什么时候改，都是你的决定。

十、追问链
------

* 提示词缓存缓存的是什么？→ 模型处理输入时算出的 KV 状态，不是文本。下一个请求的开头相同，就复用这段状态，省掉重算；
* 为什么说它是前缀匹配、精确匹配？→ 只认开头，而且到断点为止每个字节都要一样。前缀里任何一处变了，后面全部重算；没有按文件、按片段的缓存；
* 能省多少？→ 读取大约是输入价的十分之一，个别模型更低；写入要加价，Anthropic 的 5 分钟档是 1.25 倍。读一次就回本；
* 最常见的打断方式是什么？→ 中途改工具定义，Claude Code 团队说这是最常见的错误。其次是系统提示里放时间戳、改写历史而不是追加、中途换模型；
* 压缩对话为什么贵，怎么省？→ 压缩后的历史和旧的没有共同前缀；压缩请求本身要读整段历史。省的办法是让压缩请求沿用父对话的系统提示、工具和历史，把总结指令作为新消息追加；
* 上下文该怎么排？→ 少变的在前：系统提示和工具、项目指令、会话上下文、对话消息。要更新的信息用消息传，不改前面的内容；
* 怎么知道命中了没有？→ 看用量字段里的读取量和写入量。写入一直很高，说明前缀在变；再用诊断工具找分叉点；
* 缓存能代替上下文工程吗？→ 不能。命中的 token 仍然占窗口和注意力，缓存只改变价格和等待时间，该裁的内容还是要裁。

一句话总结
------

**提示词缓存只认开头，而且要一字不差：开头没变的那段按十分之一左右的价格复用，变了一处，后面全部重算。所以智能体的上下文要少变的在前、只追加不改写，更新用消息传，压缩和换模型放在任务的间隙；命中了没有看用量字段，别靠猜。**

面试官视角小结
------

提示词缓存这道题，及格线是知道它按前缀匹配、系统提示和工具定义要稳定。区分度在于有没有真的为它设计过：说得出"时间戳不能放系统提示里""历史只追加不改写""压缩请求要复用父对话的前缀"这些具体做法的，是被账单教育过；只说"开了缓存就便宜了"的，多半没看过命中率。两个高信号：一是知道写入要加价、能算出读一次回本，说明理解的是计价模型而不是一句口号；二是知道缓存不减少上下文、不解决注意力问题，说明分得清"省钱"和"上下文工程"是两件事。被追问"怎么排查命中率低"，答得出看用量字段里的读取和写入、再用诊断工具定位分叉点的，是真的上手查过。
