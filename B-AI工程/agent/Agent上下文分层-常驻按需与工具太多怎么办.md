Agent上下文分层-常驻按需与工具太多怎么办
====

一、先更新一个观念：窗口不再是主要矛盾，注意力和成本才是
------

"上下文窗口很珍贵，要精打细算"是过去两年的共识。Claude Code 的文档现在把这条列进了"可以停止做的旧建议"：多数在用的模型有 100 万 token 的窗口，而且会自动压缩，很少会真的用完。

但这不等于可以随便堆。文档同时给了两个理由：其一，你仍然在为用不上的上下文付费，每个请求都会把整段对话重发一遍；其二，东西太多本身是噪音，技能可能触发不准，模型也可能忘了你的约定。

所以问题从"怎么塞得下"变成了"什么时候该让模型看到什么"。这就是分层。

二、Claude Code 的三层供给
------

官方文档给过一个示例会话的 token 账（文档注明是示意数字，随配置而变），可以借它看清三层：

| 分层 | 进上下文的是什么 | 何时加载 | 示例会话里的开销 |
|---|---|---|---|
| 常驻层 | 系统提示 | 会话开始，每个请求都带 | 4,200 |
| 常驻层 | `CLAUDE.md`（项目级 + 用户级）、自动记忆 | 会话开始；压缩后从磁盘重新注入 | 1,800 + 320 + 680 |
| 常驻层 | 技能的名称和描述 | 会话开始；压缩后重建 | 450 |
| 常驻层 | MCP 工具名和服务说明 | 会话开始 | 120 |
| 按需层 | 技能正文、MCP 工具的完整定义、子目录的 `CLAUDE.md` | 用到的时候才进 | 进入后留在对话里 |
| 隔离层 | 子代理读到的东西 | 派活时另开窗口 | 子代理自己花了 9,890，回到主会话的只有 420 的摘要 |

**常驻层最贵，因为它每个请求都要带。** 示例里输入之前就已经占了约 7,850 个 token，其中项目 `CLAUDE.md` 的 1,800 是最大的一项可配置开销。

**按需层是分层的主体。** 技能只把描述放在常驻层，正文用到才加载；MCP 工具只放名字，完整的参数定义等模型搜索到才展开；大仓库里子目录的 `CLAUDE.md`，等模型读写那个目录下的文件时才加载。

**隔离层把大块内容挪出主会话。** 示例里一个研究任务交给子代理，它在自己的窗口里读了大量文件，主会话只收到摘要。

三、常驻层怎么写小
------

**只写模型自己查不到的。** 文档给了一个两问的测试：读代码能不能发现这件事？它会不会主动去查？两个答案都是"会"，就别写。该写的是：仓库里没有的决定（会上定的方案、某人脑子里的发布流程）、看起来没用其实还在用的目录、你已经纠正过两次的事。目录结构、依赖清单、架构总览都不要写，模型自己会读仓库。

**控制在 200 行以内。** 每一行都会在每个任务上分走一点注意力，不管相不相关。文件长了还会降低遵循度。把 `@` 别的文件当作"拆小"是没用的，导入的内容照样全量进上下文；真要拆，就移到按需加载的地方。

**写得具体到可以验证。** "用 2 个空格缩进"比"代码格式要规范"好，"`npm test` 要在提交前跑"比"测试你的改动"好。

**OpenAI 的团队把这件事做成了一个结构。** 他们试过"一个大 `AGENTS.md`"，失败得很可预期：上下文是稀缺资源，大文件把任务、代码和相关文档都挤出去了；什么都重要就等于什么都不重要；整块的手册很快就腐烂，没人维护；也没法做机械检查。后来改成把 `AGENTS.md` 当目录而不是百科全书：约 100 行的文件进上下文，只放地图，指向仓库里一个结构化的 `docs/` 目录作为唯一事实来源，并用 lint 和 CI 强制这份知识库保持最新、互相链接正确。

四、按需层的三种形态
------

**其一，技能：三层逐级展开。** 一个技能目录通常是这样的：`SKILL.md` 放概览和导航；`reference.md`、`examples.md` 放详细资料，需要时才读；`scripts/` 下的脚本是拿去执行的，根本不进上下文。有两点容易忽略：

* **技能正文一旦加载就会一直留在对话里**，所以每行都是反复计费的成本，正文要短。
* **压缩之后技能会被重新挂回来，但有预算**：每个技能保留开头最多 5,000 token，所有技能合计 25,000，从最近调用的开始算，老的可能整个丢掉。所以最重要的指令要写在 `SKILL.md` 的开头。

**其二，目录分层。** 大仓库里根目录的 `CLAUDE.md` 放全局规则，每个子目录再放自己的约定，谁拥有这个目录谁来维护。可以按路径声明一条规则只在改到某些文件时生效。这里有个坑：按需加载的内容会被压缩摘要掉。一条规则如果必须跨压缩保留，就去掉路径限定，或者挪到根目录的 `CLAUDE.md`。

**其三，工具搜索。** 这是"工具太多怎么办"的官方答案。先看问题有多大——Anthropic 给过一个五个 MCP 服务的例子：

| 服务 | 工具数 | 定义占用 |
|---|---|---|
| GitHub | 35 | 约 26K token |
| Slack | 11 | 约 21K |
| Sentry | 5 | 约 3K |
| Grafana | 5 | 约 3K |
| Splunk | 2 | 约 2K |
| 合计 | 58 | 约 55K |

也就是说，对话还没开始就先花掉约 55K。Anthropic 说自己见过优化前工具定义占掉 134K token 的情况。除了贵，更常见的失败是选错工具、填错参数，尤其是名字相近的时候。

工具搜索的做法是：工具定义用 `defer_loading` 标记为延迟加载，平时不进上下文，只留一个搜索工具；模型需要某种能力时先搜，搜到的工具才展开完整定义。效果：

* 上下文占用从约 77K 降到约 8.7K，少了 85%。
* 准确率反而上升：Opus 4 从 49% 到 74%，Opus 4.5 从 79.5% 到 88.1%。
* 不破坏提示缓存，因为延迟加载的工具一开始就不在请求里。

Claude Code 里工具搜索默认开启，常驻的只有工具名和服务说明。还有一档"阈值模式"：工具定义合计不到上下文窗口的 10% 时全量加载，到了 10% 才开搜索。Anthropic 的使用建议是：工具定义超过 10K token、可用工具在 10 个以上、或已经出现选错工具的情况时再上；最常用的三到五个工具保持常驻。

五、顺序也是设计：为提示缓存安排前后
------

每一轮对话都是一次新的 API 请求，模型不记得上一轮，脚手架要把全部上下文重发一遍。提示缓存按前缀匹配：这次请求的开头和上次处理过的内容完全一致，那一段就按缓存价计费；前缀里任何一处变了，后面的全部重算，没有按文件或按片段的缓存。

所以 Claude Code 把请求排成"少变的在前"：

| 层 | 内容 | 什么时候变 |
|---|---|---|
| 系统提示 | 核心指令、工具定义 | 加载的工具集合变了 |
| 项目上下文 | `CLAUDE.md`、自动记忆、不限路径的规则 | 会话开始，或 `/clear`、`/compact` 之后 |
| 对话 | 消息、工具结果 | 每一轮 |

系统提示一变，后面全部失效。有意思的是，计划模式和技能加载都是把指令作为一条消息追加在对话末尾，所以不会破坏前面已经缓存的前缀。会中途打断缓存的典型动作是：切模型、改推理强度、连接或移除 MCP 服务、启停插件、拒绝整个工具、压缩对话。

对自造智能体的启示很直接：**易变的内容放在后面，按需加载的内容用"追加"而不是"改写前面"**。

六、中间结果别进上下文
------

最后一层是时间上的：一次任务里产生的中间数据，用完就该走。

* **让模型写代码去调工具。** 程序化调用（Programmatic Tool Calling）让模型写一段脚本来编排多次工具调用，中间结果在代码里处理，只有最终结果回到上下文。Anthropic 的差旅预算例子：20 个人、每人 50 到 100 条报销明细，两千多条明细如果都进上下文就是灾难；改成代码后，模型只看到超支的那几个人。复杂研究任务上平均 token 从 43,588 降到 27,297，少了 37%；一段代码里调 20 多次工具，省掉 19 次以上的推理往返。Claude Code 里的对应特性叫 Code Mode，目前是实验性的，默认关闭。
* **把并行的研究交给子代理。** 子代理在自己的窗口里读大量文件，只把相关的摘要带回来。
* **把编排本身写成脚本。** 工作流（workflow）是模型写的一段脚本，循环、分支和中间结果都由脚本持有，模型的上下文里只有最后的答案。和让模型一步一步指挥子代理相比，它可重跑，规模也更大。

七、追问链
------

* 上下文是不是越多越好？→ 不是。窗口不再是主要矛盾，但用不上的内容既花钱又是噪音。关键是分层：什么时候让模型看到什么。
* 常驻层应该放什么？→ 只放模型自己查不到的，控制在 200 行以内，写得具体到可以验证。OpenAI 的做法是约 100 行的 `AGENTS.md` 当目录，指向结构化的 `docs/`。
* 工具太多了怎么办？→ 工具搜索：定义延迟加载，用到才展开。Anthropic 的例子里上下文占用少了 85%，准确率反而上升。最常用的三到五个工具保持常驻。
* 技能正文加载后会怎样？→ 一直留在对话里，所以每行都是反复计费的成本；压缩后会重挂，但每个技能最多保留 5,000 token、合计 25,000，重要的写在开头。
* 为什么内容的先后顺序重要？→ 提示缓存按前缀匹配，前面一变后面全部重算。少变的放前面，按需的内容追加在后面。
* 怎么避免中间结果撑爆上下文？→ 让模型写代码去调工具，把大块阅读交给子代理，把编排写成脚本。

一句话总结
------

**上下文分层是在回答"什么时候让模型看到什么"：常驻层只留模型查不到又每次都要用的，按需层靠技能、目录分层和工具搜索逐级展开，隔离层把大块内容交给子代理，再加上为缓存安排好先后——窗口不再是瓶颈，注意力仍然是。**
