Agent验证回路-让智能体自己发现错了
====

一、没有检查，你就是那个检查
------

Claude Code 文档里的一句话把问题说透了：**没有可跑的检查告诉它工作是不是真的完成了，"看起来做完了"就是它的全部依据。** 文档接着说，这种情况下实际充当测试套件的是你，每个错误都躺在那儿，直到你碰巧发现。

反过来，给它一个能跑出通过或失败的检查，它就能自己把这个环闭上：改完，跑检查，坏了就读输出、接着改，再跑。长任务里也一样。Anthropic 做长任务实验时观察到，模型有一种倾向：改了代码，甚至也跑了单元测试、用 curl 打了开发服务器，却不承认这个功能端到端是不通的。

这件事的杠杆比看上去大。Claude Code 团队说他们约 90% 的代码由 Claude 编写和评审；验证回路是"能把多少活交给它"的前提——没有回路，你一次只能开一两个，因为什么都得自己看；有了回路，才能并行开几十上百个。

二、检查的四个档次，越来越硬
------

同一个"跑测试"的要求，可以放在四个不同的地方，由软到硬：

| 档次 | 怎么做 | 谁来保证 |
|---|---|---|
| 写在提示里 | "改完跑一下认证测试，通过为止" | 模型自己判断满不满意 |
| 设成目标 | 用 `/goal` 设一个完成条件，比如认证目录下的测试全部通过、lint 干净 | 每轮结束后另一个模型对着对话判定 |
| Stop 钩子 | 模型想结束回合时跑你的脚本，退出码为 2 就打回去 | 脚手架强制 |
| 局外人审查 | `/code-review` 在一个没见过这段对话的子代理里审 diff | 独立的视角 |

几点细节：

* **Stop 钩子是真正硬的那一档。** 文档给的例子只有一行：`pnpm tsc --noEmit 1>&2 || exit 2`。编译器输出重定向到标准错误，而标准错误的内容会原样回到模型那里，成为"还不能收工"的理由。连续挡回八次、中间没有任何工具调用的话，Claude Code 会放行下一次，避免卡死。
* **目标机制用的是另一个模型。** `/goal` 每轮把条件和到目前为止的对话交给一个又小又快的模型，返回"未达成、已达成、不可能"三者之一。关键在于"做完没有"由一个没参与干活的模型来判，而不是干活的那个自己说了算。它有边界：不跑命令、不读文件，只能根据对话里已经呈现的东西判断，所以条件要写成模型的输出能证明的样子。
* **要证据，不要结论。** 无论哪一档，都该让智能体交出它跑了什么命令、输出是什么。"所有测试通过"这句话本身说明不了什么。

三、三种反馈，优先级要排对
------

Anthropic 在 Agent SDK 的文章里列了三种让智能体评估自己工作的办法，态度很明确：

**明确规则最好。** 给输出定义清楚的规则，然后告诉它哪条没过、为什么。代码检查是这类反馈的典型，而且反馈越深越好——生成 TypeScript 并做类型检查，通常比生成纯 JavaScript 好，因为多了一层反馈。

**视觉反馈适合界面类的任务。** 生成带格式的邮件、做界面，可以把渲染结果截图给模型看，让它对照要求检查布局、样式、内容的层次和响应式表现。

**让另一个模型当裁判最不稳。** 文档的评价是这种方法"通常不太稳健"，还有明显的延迟代价，只在性能提升值得这些成本时才用。

那模型裁判是不是就没用了？也不是。Claude Code 团队在结构化文件生成的内部测试里，让一个独立的评分者按评分细则检查 Claude 的工作，任务成功率比标准的提示循环最多高出 10 个点，最难的题上提升最大。两处说法放在一起看就清楚了：模型裁判适合做补充，不适合当唯一的判据。

四、值得投资的三类测试
------

Claude Code 团队挑了三类他们认为最值得投入的测试，前提是先避开两个坑：测试不稳定，会教坏智能体——它学会的是再跑一遍，而不是去修；测试太慢，它每批跑的就少，问题更难定位。

* **端到端测试。** 如果只能选一类，选它。它描述真实的用户流程，难作假：整个功能要么通要么不通，有明确的完成标准。单元测试更快更稳，但可能通过了而功能是坏的，因为智能体和测试都没理解完整的任务。
* **属性测试。** 先写一条你认为不可能不成立的性质，再用测试库生成成千上万个输入去推翻它，比如编码再解码要还原、余额不能为负、幂等操作做两遍和做一遍一样。它的价值在于用与写代码的智能体不带同样偏见的边界情况，去检验那份代码。
* **差分测试。** 迁移场景的利器：老系统就是标准答案。新旧两套用同样的输入跑，结果不一样就说明有问题。

**验证的意思是把改动真的跑起来。** 团队的做法是让 Claude 像人或测试工程师那样测整个应用：网页改动用浏览器扩展，移动端用 iOS 或安卓的 MCP，桌面端用计算机操作，后端在本地把服务跑起来。怎么启动应用，写成一个名为 `verify` 的技能放在仓库里；Claude Code 看到会话里有这个名字的技能，就会在每次提交前先运行它（文档和测试的改动除外）。然后要持续把这个技能打磨得又快又稳——它就是你的冒烟测试，必须靠得住。

五、让检查本身可信
------

智能体会改代码，也可能改到评判它的检查。Claude Code 团队的几条纪律都是围绕这个来的：

* **改动不能修改评判自己的检查。** 代码审查读的 `REVIEW.md` 取自主干，从不取自这次改动；评审绑定到具体的提交，在一个已经过期的提交上通过评审毫无意义。便宜的检查放前面：测试、构建、lint 在开 PR 之前就跑完，别浪费共享的评审和 CI 时间。
* **规则的负责人自己写检查。** 谁拥有这段代码，谁来写它的检查，反复调到"负责人会挑的它也挑"为止。检查把评审人拉进来时，要说明原因。
* **只检查被触发的那几条。** 团队维护一份 39 项的可靠性清单，每一项都有能从 diff 里读出来的触发条件、一项检查，以及背后的故障案例。模型读 diff，只核对触发条件匹配上的那些，通常是 3 到 10 项，没有人需要记住所有历史故障。
* **新门禁先观察再强制。** 团队给每个提交打上"是怎么验证的"标记，连"没验证"也打。提交门禁有关闭、观察、强制三档：观察档只记录本来会拦下什么，用来排除误伤；强制档下，同一个会话里被连挡两次，下一次会放行，不让模型卡死。
* **不稳定的测试和漏掉的缺陷都要处理。** 模型不能跳过不稳定的测试，也不能加延时、反复重试直到通过；找不到根因就删掉这条测试并写明原因。漏掉的缺陷则变成规则：从评审意见和回滚里提炼模式，至少在两个 PR 里出现过、且能从 diff 识别，才考虑成为规则。

还有一条反直觉的经验：审查时让模型"只报影响正确性的缺口，跳过风格"。文档的提醒是，被要求找问题的审查者总能找出点什么，如果把每条发现都修掉，最后多出来的是用不上的抽象层和为不可能的情况写的测试。

六、把重复的失败变成规则
------

验证回路不只管当下这一次，还应让同类错误不再发生。几次失败的检查暴露出的问题，有一条升级路径：

* 同一个错犯了两次，就写进 `CLAUDE.md`；Anthropic 的例子是，智能体反复通不过"日志里不能有用户数据"的检查，就加一个钩子或一条更明确的规则。
* 文档管不住的时候，升级成代码。OpenAI 的团队用的说法是"文档不够用时，把规则提升为代码"：架构约束由模型写的 lint 和结构测试来守，报错里直接带修复步骤。
* 强制的集合要保持小。Claude Code 文档的提醒很实在：每个钩子和拒绝规则都会有误伤的时候，也都要有人维护；如果你发现自己写到了四十个，其中大多数多半只是偏好。

**环境本身也要让智能体看得懂。** OpenAI 的团队为了减少人工验收，让应用可以按 git 工作树各起一个实例，把 Chrome 开发者工具协议接进智能体的运行时，并给每个工作树配一套用完即弃的日志、指标和链路。这样"服务启动要在 800 毫秒内完成"这种要求才变得可以验证——智能体能自己查。他们常见到一次 Codex 运行在单个任务上连续工作六个小时以上。

七、追问链
------

* 怎么让智能体自己知道做对了？→ 给它一个能跑出通过或失败的检查。没有检查，"看起来做完了"就是它的全部依据，而你成了测试套件。
* 要求它跑测试，写在哪里最有效？→ 四个档次由软到硬：提示、目标、Stop 钩子、局外人审查。Stop 钩子退出码为 2 就打回去，标准错误的内容回到模型那里。
* 让模型给模型打分靠谱吗？→ 不适合当唯一判据。明确的规则最可靠，视觉反馈适合界面，模型裁判只作补充——独立评分者能把成功率最多提高 10 个点，但本身不够稳健。
* 端到端、属性、差分测试各管什么？→ 端到端难作假、有明确的完成标准；属性测试用不带同样偏见的边界情况；差分测试拿老系统当标准答案。
* 怎么防止智能体把检查改得对自己有利？→ 检查不能被它评判的改动修改：规则文件取自主干，评审绑定到具体提交，便宜的检查放在前面。
* 同一个错误反复出现怎么办？→ 升级：先写进指令，再做成钩子，最后提升为代码。同时保持强制的集合足够小。

一句话总结
------

**验证回路是把活交给智能体的前提：给它一个能跑出通过或失败的检查，用 Stop 钩子把关键的那条做硬，用独立的视角防止自己给自己判及格，守住检查不被改动篡改，再把反复出现的失败一级级升级成规则。**
