Agent脚手架复刻清单与面试追问
====

> 定位：第三章「脚手架设计」收尾篇（agent 系列第 17 篇）。把前五篇收成两样东西：一张自己造智能体时可以照着搭的清单，和一组面试里会被连环追问的问题。[面试题合集](../面试题/LLM应用面试题合集.md)的 Agent 一节只有三道题，"脚手架"这个主题在这里补上。读之前先过一遍[总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md)。
>
> **内容来源**：本篇是本章的归纳，事实与数字均出自前五篇引用过的材料（Claude Code 官方文档，Anthropic 与 OpenAI 的工程文章），出处见各篇头部。表中"自造时的最小实现"一列，是在这些材料基础上的工程建议，属于本文的归纳，不是哪份文档的原话。

一、复刻清单：一个能好好干活的智能体需要什么
------

| 部件 | Claude Code 的做法 | 自造时的最小实现 | 详见 |
|---|---|---|---|
| 循环骨架 | 收集上下文、行动、验证，循环往复 | 一个循环：调模型，执行工具，把结果回填，直到满足停止条件 | [总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md) |
| 工具 | 少而准，按工作流合并；返回高信号信息；报错带修法；描述当提示词写 | 先只做最常用的三到五个，其余按需加载；每个工具配 1 到 5 个调用示例 | [工具设计篇](Agent工具设计-写给模型看的接口.md) |
| 返回值 | 工具返回默认限制在 25,000 token，超限存成文件只留路径 | 给大结果设默认上限，截断时说明怎么取更多 | [工具设计篇](Agent工具设计-写给模型看的接口.md) |
| 上下文分层 | 常驻层很小；技能、MCP 定义、子目录规则按需加载 | 常驻指令控制在 200 行以内；知识分三层：描述、正文、支撑文件 | [上下文分层篇](Agent上下文分层-常驻按需与工具太多怎么办.md) |
| 缓存友好 | 少变的在前，易变的在后；按需内容以追加方式进入 | 固定前缀（系统提示、指令）不轻易改写 | [上下文分层篇](Agent上下文分层-常驻按需与工具太多怎么办.md) |
| 验证 | 可运行的通过/失败检查；Stop 钩子；没见过对话的审查者 | 至少一条能跑的检查；最关键的那条做成硬门禁；只认证据不认结论 | [验证回路篇](Agent验证回路-让智能体自己发现错了.md) |
| 硬规则 | 钩子、拒绝规则、托管设置，由脚手架强制 | 没有例外的规则不写进提示词；强制的集合保持小 | [总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md) |
| 状态与长任务 | 进度文件、功能清单、每次收工提交；会话恢复、检查点 | 功能清单用 JSON，全部标成未通过；一次只做一个，做完就提交 | [长任务篇](Agent长任务-进度状态与增量交付.md) |
| 护栏 | 权限模式、沙箱、审查者 | 拒绝名单、必问名单、能力边界，三道关口 | [人机协同篇](Agent人机协同-从头部智能体看审批与权限设计.md) |
| 用量可见 | 按技能、子代理、插件、MCP 服务分解用量（部分套餐） | 按部件记账，才知道该裁哪一块 | [评测篇](Agent评测与可观测-guards与成本.md) |
| 评测 | 工具和技能的改动，开着和关着各跑一遍 | 留一份没见过的测试集，防止改到只适配考题 | [评测篇](Agent评测与可观测-guards与成本.md) |

这张表不是一次搭全的。Claude Code 的用量视图会把长上下文、频繁缓存未命中这类使用模式标出来，只要它超过用量的 10%——先看账，再决定加什么。

二、落地顺序：从症状出发
------

Claude Code 文档给了一张"出现什么征兆、加什么部件"的表，按它来加，每一块都有来处：

| 征兆 | 加什么 |
|---|---|
| 同一个约定或命令做错了两次 | 写进常驻指令 |
| 同一段开场提示反复在敲 | 存成技能 |
| 同一份多步流程第三次贴进对话 | 存成技能 |
| 总是从 Claude 看不到的页面里复制数据 | 把那个系统接成工具 |
| 为了找一个符号的定义读了大量文件 | 接入代码智能 |
| 一项副任务把对话淹没了 | 交给子代理 |
| 希望某件事每次都发生、不用交代 | 写成钩子 |
| 第二个仓库需要同样的配置 | 打包 |

工具和技能的改动走另一个循环：先搭原型自己用，再建评测，然后让智能体读着评测记录帮你改。

两条稳妥起步的原则，来自最近的两份材料：新的门禁先开"观察"档，看清楚它会误伤什么，再切成强制；常驻智能体宁可一开始话少，再逐步赢得用户的注意力。

三、面试连环追问
------

下面十二个问题，是"怎么做才像 Claude Code 一样好用"这个话题里会被一层层挖下去的。每题的答案故意只留结论，细节在对应的篇目里。

* **同一个模型，为什么 Claude Code 好用？** → 差别在模型外面的脚手架：它管着模型看到什么、能做什么、谁确认做完、什么不能做。（[总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md)）
* **规则写在提示词里，还是做成钩子？** → 分两种指令。让模型决定的大多数，用提示词；必须每次发生或绝不能发生的，用钩子或拒绝规则。（[总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md)）
* **工具怎么设计？** → 少而准，按工作流合并；返回高信号的信息；报错写清怎么改；描述当成提示词来写。（[工具设计篇](Agent工具设计-写给模型看的接口.md)）
* **工具太多怎么办？** → 工具搜索：定义延迟加载，用到才展开。Anthropic 的例子里上下文占用少了 85%，准确率反而上升。（[上下文分层篇](Agent上下文分层-常驻按需与工具太多怎么办.md)）
* **常驻指令怎么写？** → 只写模型自己查不到的，200 行以内，具体到可以验证。参考资料移到按需加载的地方。（[上下文分层篇](Agent上下文分层-常驻按需与工具太多怎么办.md)）
* **智能体说做完了，其实没做好，是哪里出了问题？** → 它没有一个能跑出通过或失败的检查，"看起来做完了"就是它的全部依据。（[验证回路篇](Agent验证回路-让智能体自己发现错了.md)）
* **让模型给模型打分，靠谱吗？** → 不能当唯一判据。明确的规则最可靠，模型裁判只作补充。（[验证回路篇](Agent验证回路-让智能体自己发现错了.md)）
* **怎么防止智能体把检查改得对自己有利？** → 检查不能被它评判的改动修改：规则文件取自主干，评审绑定到具体的提交。（[验证回路篇](Agent验证回路-让智能体自己发现错了.md)）
* **长任务跨好几个上下文窗口，怎么不跑偏？** → 状态放到窗口外面：进度文件、一份全标未通过的功能清单、每次收工提交；一次只做一个功能。（[长任务篇](Agent长任务-进度状态与增量交付.md)）
* **上下文窗口不够用怎么办？** → 这个问法本身过时了。窗口不再是主要矛盾，注意力才是；解法是分层：常驻的写小，其余按需加载。（[上下文分层篇](Agent上下文分层-常驻按需与工具太多怎么办.md)）
* **任务一长，要不要多派几个智能体？** → 不急。先把单个智能体的进度状态和验证回路做扎实；团队会增加协调开销和 token 消耗。（[长任务篇](Agent长任务-进度状态与增量交付.md)）
* **以前学的提示词技巧还有用吗？** → 要重新评估。模型进步之后，反复强调、催它别停、靠子代理保护窗口，这些做法已经成了累赘。（[总览篇](Agent脚手架总览-ClaudeCode好用在模型之外.md)）

四、一条主线
------

回头看，六篇其实只在讲一件事：**把对模型的期望，挪到模型之外去实现。**

希望它看到该看的，就去做上下文分层，而不是把提示词写长。希望它用对工具，就去改工具的接口，而不是在提示里反复叮嘱。希望它做对，就给它一个能跑出通过或失败的检查，而不是要求它"仔细一点"。希望它不做某事，就用钩子守着，而不是加一句"千万不能"。希望它坚持到底，就把状态放到窗口外面，而不是催它"做到完成为止"。

面试里能把这条主线讲清楚，再从任何一处往下挖到细节，这个话题就立住了。
