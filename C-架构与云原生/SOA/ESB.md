ESB（企业服务总线）
====

一句话描述
====

ESB（Enterprise Service Bus，企业服务总线）是 SOA 架构中的核心中间件：把企业的各个系统都接到一条「总线」上，由它统一负责服务之间的**路由、协议转换、消息转换与编排**，让异构系统之间不必点对点直连，而是通过总线互相调用。

一、ESB 的定位：SOA 的「中枢神经」
------

SOA（面向服务架构）的诉求是把 ERP、CRM、OA 这些由不同供应商、不同技术开发的孤立系统，包装成粗粒度的**服务**供外部访问，实现应用集成与数据集成。但服务多了以后，如果点对点直连，N 个系统两两互联就是 N×(N-1)/2 条线路，任何一处接口变更都会牵一发动全身。

ESB 就是为解决这个问题而生：**所有服务都挂到总线上，服务消费方不直接找服务提供方，而是找总线**。总线屏蔽了服务在哪里、用什么协议、什么数据格式，消费方只要告诉总线「我要调谁」，剩下的事总线全包了。所以常说「SOA 高度依赖服务总线（ESB），而微服务不需要」——ESB 是 SOA 与微服务最直观的分界线。

二、ESB 的核心能力
------

1、**服务路由（Routing）**

> 消费方只面向逻辑端点（服务名）发起调用，ESB 根据服务注册信息把请求路由到真正的物理地址。地址变了、迁移了、做灰度分流了，消费方完全无感。

2、**协议转换（Protocol Transformation）**

> 企业里遗留系统五花八门：HTTP/REST、SOAP/WebService、JMS、FTP、TCP 私有协议……ESB 在中间做翻译，让用 SOAP 的老系统和用 HTTP 的新系统无缝互通，消费方只用一种协议说话。

3、**消息转换（Data/Message Transformation）**

> 不同系统对同一业务实体的数据格式各不相同（XML vs JSON、字段命名不同、结构不同），ESB 在传输途中做报文的映射、拆包、组包，实现数据层面的集成。

4、**服务编排（Orchestration）**

> 把多个原子服务按流程图编排成一个组合服务（如「下单」= 调库存 + 调账户 + 调物流），通过 BPEL 等方式在总线层固化业务流程，对外呈现为一个新服务。

5、**其他企业级能力**

> 消息路由支持的发布/订阅、负载分流、安全认证与权限控制、监控审计、流量控制、服务治理（服务注册/版本/生命周期管理）。典型产品：商业的 WebSphere ESB、Oracle ESB（BEA AquaLogic）、Mule ESB、开源的 Apache ServiceMix / Camel 等。

用一个调用串起来：消费方发起 SOAP 请求 → ESB 接收 → 认证鉴权 → 按服务名路由到目标 → 把 SOAP 报文转成目标系统要的格式/协议 → 目标系统返回 → ESB 再转回消费方要的格式 → 返回。全程消费方与提供方互不知晓对方细节。

三、ESB 的问题
------

* **单点与瓶颈**：所有服务调用都过总线，总线一挂全站瘫痪；流量集中也使 ESB 成为性能瓶颈，越靠中心越容易过载。

* **通信效率低**：请求多一跳中转，还要做协议/报文转换，链路长、延迟高，吞吐上不去。

* **开发与维护代价大**：集成一个系统要在总线上配置端点、协议、映射、编排，SOA 治理流程重，参与角色多，变更周期长。

* **「智能管道，哑端点」**：逻辑集中在总线，端上的系统相对被动。这与后来互联网架构的哲学正好相反。

* 实践结果：SOA 在企业信息化领域热闹过一阵，但受限于以上代价，并未得到大规模成功应用。

四、为什么被微服务替代
------

微服务不是推翻 SOA 的思想（Martin Fowler 自己说「微服务是 SOA 的子集」），而是换了一套实现哲学：**去中心化**。

| 维度 | ESB（SOA） | 微服务 |
| ---- | ---- | ---- |
| 通信模式 | 中心化，一切过总线 | 去中心化，服务间点对点直连（RPC/HTTP）+ 注册中心只做服务发现 |
| 管道与端点 | 智能管道、哑端点 | **智能端点、哑管道**（martin fowler：smart endpoints and dumb pipes） |
| 集成能力 | 协议转换、编排等重逻辑压在总线 | 各服务自治，格式统一（JSON over HTTP/gRPC），无需集中翻译 |
| 部署与扩展 | 总线整体扩展，牵一发动全身 | 按服务独立部署、独立弹性伸缩 |
| 容错 | 总线单点，故障全局化 | 熔断降级限流，故障局部化 |
| 配套生态 | 重量级中间件 + 重治理流程 | 容器（Docker/K8s）、CI/CD、DevOps、APM、自动化测试整套工具链 |
| 典型时代 | 2000 年前后企业信息化（应用/数据集成） | 互联网高并发、快速迭代时代 |

替代的深层原因可以概括为三点：

1）**规模与迭代速度**：互联网业务流量大、变更频繁，中心化总线的吞吐和变更成本都无法承受；去中心化点对点调用把延迟和扩展性问题就地解决。

2）**生态成熟**：微服务的成功不只是架构本身，容器编排、微服务治理框架、DevOps 工具链一起补齐了 ESB 原来承担的部署、治理、监控能力，而且做成了分布式、可弹性伸缩的。

3）**技术栈趋同**：系统内部服务统一技术栈、统一通信协议，ESB 最值钱的「翻译」能力失去了用武之地——协议转换的需求主要留给了对外网关。

五、ESB 的遗产
------

ESB 没有消失，而是换了个形态活在微服务体系里：

* **API 网关**：承接了 ESB 对外的协议适配、路由、安全认证、限流监控——但只做「南北向」流量入口，不做服务间总线，逻辑轻、可水平扩展。

* **服务网格（Service Mesh）**：把路由、熔断、灰度、加密等通信治理能力下沉到 Sidecar（如 Istio + Envoy），可以看作「去中心化的 ESB」——能力还在，中心没了。

* **集成场景仍存活**：大型企业内部异构遗留系统的集成、B2B 对接，ESB/集成平台（如 MuleSoft）依然有市场。

面试要点：先说清 ESB 在 SOA 里的定位（路由、协议转换、消息转换、编排），再答被微服务替代的原因（中心化单点瓶颈、通信效率低、开发维护代价大、去中心化 + 容器/DevOps 生态的成熟），最后点一句 API 网关/服务网格是其思想的延续，层次就齐了。
