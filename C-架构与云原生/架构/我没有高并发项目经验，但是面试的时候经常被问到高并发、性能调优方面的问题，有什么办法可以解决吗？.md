看在前面
------

* <a href="https://www.zhihu.com/question/421237964/answer/1699066805">我没有高并发项目经验，但是面试的时候经常被问到高并发、性能调优方面的问题，有什么办法可以解决吗？</a>

这是一个知友提出的问题，相信不少同学都有类似的困惑：没有做过真正的高并发项目，却总在面试中被追问高并发、性能调优，怎么破？

先泼盆冷水
====

高并发经验确实是系统工程师的门槛，字节跳动等大厂的基础架构岗位基本都要求高并发、高可用的项目经验。而且，面试官火眼金睛，简历上简单包装的"高并发"经验很容易被追问穿帮。

把没做过的事情说得很高大上，在面试里相当于给自己挖坑：面试官顺着细节一问，答不上来反而显得不诚实，比没有经验更减分。

高并发的真正门槛
====

大厂基础架构岗位的高并发，动辄要求日活过亿、每天几百上千亿请求量的系统经验，这种业务复杂度、数据量级是中小公司很难接触到的。对多数人来说，这个门槛客观存在，不必焦虑，但也不能靠吹。

面试官其实想听什么
====

面试官问高并发，不是要求你真的扛过亿级流量，而是想看你对高并发系统设计的**思路**。比如系统怎么拆分、怎么保证高可用、缓存怎么用、怎么避免单点，这些通用思路是可以系统学习的。

假如面试官问"设计一个支撑三五百万人的抢购/订票系统"，你的思路应该围绕：系统怎么做到稳定、容量怎么规划、怎么冗余避免单点故障。

举个例子
====

以一个典型的电商交易系统为例，整体链路大致是：

```
用户 -> CDN -> 接入层(LVS/F5) -> Nginx集群 -> 服务网关
        -> [交易系统] <-分布式缓存-> Redis
             |  ^                -> 本地缓存
             |  +--- RPC(注册中心) ---+
             v
          消息队列(MQ) -> 订单系统 -> DB(主从/分库分表) / ES
             |
          熔断降级(Hystrix/Sentinel)
```

逐层拆解这些组件，就是你的"高并发"知识体系：

* **接入层**：LVS/F5 + Nginx 做流量入口，Nginx 本身可以做负载均衡、限流；CDN 把静态资源推到离用户最近的节点，大幅减少回源流量。

* **服务网关**：所有请求的统一入口，做鉴权、限流、灰度路由；网关自身要无状态、可水平扩容。

* **缓存**：系统抗量的核心。用户数据、商品数据先查本地缓存（进程内），再查分布式缓存（Redis），最后才落库；要注意缓存穿透、击穿、雪崩的应对。

* **RPC 与服务拆分**：单体按业务边界拆成微服务，通过 Dubbo/Spring Cloud RPC 通信，配合注册中心动态发现；哪个服务压力大就单独扩哪个。

* **消息队列**：下单等核心链路削峰填谷，非核心逻辑（发短信、记日志、更新统计）异步化，把同步调用的响应时间从串行累加变成毫秒级返回。

* **分库分表**：单库单表到瓶颈后，按用户 ID 哈希拆分数据；配套主从读写分离、冷热分离。

* **检索**：复杂的列表查询走 Elasticsearch，避免 like 打爆数据库。

* **熔断降级**：依赖的服务超时或挂掉时快速失败、返回兜底数据，防止故障级联雪崩。

这些都是现成的方案，吃透"为什么这么设计"，你就能在面试里讲清楚一个高并发系统是怎么被搭出来的。

具体怎么准备
====

1. **按专题系统学习**：缓存（Redis、本地缓存）、消息队列（削峰、异步）、数据库优化（索引、主从、分库分表）、限流熔断降级、分布式扩展（服务拆分、无状态化），每个专题都往深了挖一层，面试官问到底层才不慌。

2. **结合系统设计题演练**：把秒杀、抢红包、订票这类经典题拿来完整推演一遍，从流量估算、容量规划到每一层的瓶颈和应对，能白板画出架构图。

3. **做过压测也是素材**：哪怕是几十 QPS 的系统，如果你做过 JMeter 压测、定位过慢 SQL、加过缓存优化了接口 P99，这些"小规模但完整"的性能调优经历同样能讲——调优的方法论是相通的，只是量级不同。

4. **复盘与追问**：每学一个组件，多问自己"它解决了什么问题、不用它会怎样、极端场景下它会怎么挂"，面试官的连环追问通常就停在这里。

总结
====

没有高并发经验不可怕，可怕的是既没有经验又没有思路。把高并发的通用套路（缓存、异步、拆分、冗余、限流降级）学透、能落到具体组件和场景上，再诚实地向面试官展示你的思考过程，大部分非基础架构核心岗的高并发问题，你都能接得住。

面试常见追问与答法
====

把套路讲完只是及格，面试官一定会往细节追问，提前备好这些"下钻点"：

* **缓存一致性怎么保证？** 答 Cache Aside：读— miss 回源回填；写—先更新库再删缓存；再谈延迟双删、订阅 binlog 异步失效，以及极端场景下的最终一致。

* **缓存穿透/击穿/雪崩？** 穿透用布隆过滤器或空值缓存；击穿用互斥重建或热点不过期；雪崩用过期时间加随机、多级缓存、集群高可用。

* **消息丢了怎么办？** 生产端 confirm/事务消息、Broker 持久化与副本、消费端手动 ack + 幂等（唯一键/状态机）。

* **接口幂等怎么做？** 唯一请求号 + 数据库唯一索引 / Redis setNX / 状态机流转校验。

* **数据库瓶颈？** 先索引和慢 SQL 治理，再读写分离，然后按业务维度分库分表，注意分片键选择（如用户 ID）带来的跨片查询问题。

* **超时和重试怎么设置？** 超时要小于用户忍耐阈值（如核心链路 500ms），重试要配退避和次数上限，且只重试幂等接口，否则用熔断快速失败。

这些追问每一层都能再往下挖，你准备的深度决定面试的"水位"。

调整心态
====

不要把"没有高并发经验"当成原罪。面试是展示思考能力的过程，不是经验审计：把自己的项目按高并发的思路重新推演一遍（哪里是单点、哪里可以缓存、哪里可以异步），你会发现很多中小系统的优化思路和大厂是同构的，只是流量规模不同。

最后，如果目标就是基础架构核心岗，那确实需要想办法进入有真实海量流量的环境（内部转岗、去有规模的公司）；对大多数业务研发岗，系统化的思路 + 诚实的表达，已经足够通过绝大多数高并发面试。
