清结算与资方对接
====

> 系列收尾篇。前四篇都在讲"我方系统内部"（[领域模型](信贷业务全景与领域模型.md)、[账务](账务系统设计-复式记账与日切.md)、[幂等对账](幂等与对账-资金安全底座.md)、[风控](风控决策架构.md)），这篇把镜头拉到边界：钱真正走的地方（资金流）和我方系统记录的地方（信息流）是两条线，中间隔着资方、渠道与一堆文件。

资金流与信息流分离
====

信贷平台（尤其助贷/联合贷形态）的立身之本：**我方系统不一定碰钱，但必须完整、准确、及时地记录钱**。两条流的分离是整个清结算架构的第一原则：

```
 信息流(我方系统,秒级)                资金流(银行/渠道,真实划拨)
┌──────────────────┐   发指令    ┌──────────────────────────┐
│ 支用申请 → 立借据   │ ────────▶ │ 资方放款户 ──▶ 备付金/内部户   │
│ 账务记分录         │            │              ──▶ 代付渠道     │
│ 还款冲抵 → 结清     │            │                 ──▶ 用户银行卡 │
│ 清分计算 → 清算指令 │ ◀──────── │ 用户还款 ──▶ 代收渠道 ──▶ 备付金 │
└──────────────────┘   回执/对账  │              ──▶ 按份额清算给资方 │
                                  └──────────────────────────┘
   信息流可以回滚/补偿/对账兜底  ◀──▶  资金流一旦划出只能冲正,不能"删掉"
```

分离带来三条设计纪律：

* **指令与回执成对**：信息流发的每一笔资金指令（放款/代扣/清算）必须有终态回执（同步应答 + 异步回调/文件确认），指令无终态 = 悬挂，进对账差异池；
* **信息流以账务为锚**：资金回执确认后账务记分录，账务余额代表"我方视角的资金事实"，与渠道/资方对账验收（见[幂等与对账-资金安全底座](幂等与对账-资金安全底座.md)）；
* **资金指令幂等**：同一条指令重发，资金侧只能划一次——指令号唯一 + 资方/渠道侧幂等键，和支付回调防重放（[支付回调的HMAC验签与幂等设计](../../A-后端内核/框架与中间件/安全/支付回调的HMAC验签与幂等设计.md)）是同一个问题在两个方向上的投影。

放款与还款的资金路径
====

以"资方出资、我方运营"的典型助贷为例，账户按"谁的钱"划分：

```
放款: 资方放款户 ──10000──▶ 备付金/内部户(过账) ──10000──▶ 代付渠道 ──▶ 用户卡
      信息流: 支用成功 → 借据 ACTIVE → 账务: 借 应收资款项/贷款户, 贷 渠道往来户

还款: 用户卡 ──10300──▶ 代收渠道 ──10300──▶ 备付金/内部户 ──按份额──▶ 资方清算户
      信息流: 还款成功 → 冲抵(费用→罚息→利息→本金) → 借据应还更新 → 清分记账
```

* **备付金/内部户是"资金的候车厅"**：放款时资方的钱先进内部户再代付出去，还款时代收的钱先进内部户再清分给资方。它存在的意义是让**每一笔钱在任何时刻都有明确的归属状态**——在途（属于某笔放款）、待清分（属于还款但资方份额未划）、挂账（差错待查）。备付金余额 = Σ(在途 + 待清分 + 挂账)，这个等式本身就是一个日终核对项；
* **备付金不可挪用**：内部户里的钱在清分前是资方的钱，不是平台的自有资金。账务上通过科目隔离（应付—资方款 vs 自有资金科目），流程上通过余额巡检——"备付金池被用于自有资金支出"是清结算域最严重的红线事故；
* **还款清分的顺序**：还款进内部户后按冲抵顺序拆分（监管通常要求费用/罚息/利息/本金的顺序），再按各资方出资比例拆份额，生成清算指令；资方多、份额规则复杂（联合贷还有分润/担保费/技术服务费）时，清分引擎是独立的计算域，产出"谁应得多少"的清算单，资金划拨按单执行。

资方文件交互
====

与银行/信托/消金公司的对接现实：实时接口往往只有放款/查询等少数几个，**大量业务靠批量文件驱动**。一个典型的日批次闭环：

```
 T 日                                    T+1 日
┌────────────────────┐         ┌─────────────────────────┐
│ 我方推送: 支用明细文件  │         │ 资方推送: 放款结果文件        │
│ (当日新增借据要素)     │         │ 我方推送: 还款明细文件        │
└─────────┬──────────┘         │ 资方推送: 对账文件(余额/明细)  │
          ▼                    └───────────┬─────────────┘
   资方放款/SFTP 落地                       ▼
                                   逐笔勾对: 金额/状态/余额三方一致
                                   差异 → 差错池(见幂等与对账篇)
```

文件交互的四个工程要点：

* **批次协议先于数据设计**：每个文件都是一个批次（batch），协议要素齐全才能对账——

```
文件命名: TRXN_{资方代码}_{业务类型}_{账务日期}_{批次号}_{序号}.txt.enc
批次清单: 行数 + 金额合计 + MD5(加密前明文)          ← 三要素校验,先验清单再解密解析
行级状态: 每行带状态字段(成功/失败/冲正),部分成功是常态
回执闭环: 我方解析完必须回 ACK 文件(含拒收行号),资方没收到 ACK 视为传输失败重推
```

* **加密与签名**：文件级传输走 SFTP/专线 + 文件本身加密（资方公钥加密对称密钥 + AES 加密内容），附**数字签名**（我方私钥签、资方公钥验）保证来源与完整性——与支付回调验签同一逻辑，只是载体从 HTTP 报文换成了文件摘要；密钥管理同款军规：配置中心注入、不落库、不进仓、可轮换；
* **对账文件三方勾对**：我方账务 vs 我方业务单据 vs 资方对账文件，三方金额/状态/期末余额全部一致才算平；资方对账文件的"应还余额"直接校验我方计息引擎的正确性（口径差异——算头不算尾、计息基数——在这里现形）；
* **文件异常兜底**：文件未到（超时告警 + 催收文件重推通道）、文件格式变更（版本号字段 + 兼容解析）、批次部分成功（按行级状态回执，失败行进重推队列）。文件批次天然是**最终一致**的：T 日推送失败 T+1 日补推，对账以文件到达日为准重开窗口。清算批次本身也是一个状态机，异常兜底落在每条边上：

```
CREATED(生成清算单)
   │ 推送/划款指令
   ▼
SUBMITTED(已提交资方/渠道) ──超时未回执──▶ 重试(有限次) ──仍失败──▶ 差错池人工介入
   │ 回执文件/实时回执                    │
   ▼                                    ▼
CONFIRMED(资方确认)                部分成功: 成功行确认,失败行冲正/重推
   │ 试算勾对(金额/笔数与清算单一致)
   ▼
SETTLED(清算完成,分录终态)              任一非终态停留 > SLA → 升级
```
* **异常兜底原则**：文件链路断了，业务不停止——放款可先走实时接口（若资方支持）或拒绝进件保护资方，但**对账差异必须累积可见**，文件恢复后一次性勾对清零；"文件一直没来就当没差异"是清结算域最大的自欺。

助贷与联合贷的架构差异
====

两种模式的根本差异在**出资结构**，架构差异全部由此派生。先看清结算域的一天怎么排（这些批次的顺序就是资金责任的顺序）：

```
清结算日终时间线（T+1 日处理 T 日账）：
 02:00 计息/计提批完成(账务域, 见账务篇) ──▶ 应还数据冻结
 03:00 拉取渠道账单/代收代付回执 ──▶ 渠道对账(差异进差错池)
 05:00 拉取各资方对账文件 ──▶ 三方勾对(我方账务/业务单据/资方文件)
 07:00 清分计算(冲抵+份额拆分+费用分润) ──▶ 生成清算单
 08:00 清算划款指令(资方清算户) ──▶ 批次状态机推进(见上)
 10:00 清算回执勾对 ──▶ 总分核对(聚合 vs 份额 vs 账务) ──▶ 出清结算日报
 任一环节不平: 后续批次阻塞告警,绝不允许"带差异继续清算"
```

| 维度 | 助贷（资方 100% 出资） | 联合贷（多方按比例出资） |
|----|----|----|
| 借据 | 一张借据、单一资方 | 一张借据还是 N 张子借据是第一设计决策 |
| 额度 | 授信总额度整体给该资方 | 各资方出资比例不同，支用时按比例拆分占用 |
| 计息 | 单一口径 | 各资方利率/还款日可能不同，按份额分别计息 |
| 清算 | 还款全额清给资方，我方收技术服务费 | 按出资比例清分，含分润/担保费多维计算 |
| 对账 | 我方 vs 单一资方 | 我方 vs 每家资方分别对账，再总轧差 |
| 风险 | 资方担 100% 信用风险（或有担保/兜底安排） | 各担各比例，逾期后代偿/分摊规则复杂 |

联合贷的关键架构决策——**子借据模型**：一次支用按出资比例拆成 N 个资方份额，每个份额独立记账（本金/利息/罚息/状态），对上聚合为用户视角的一张借据（用户只看到"我还了一期 10300"），对下每个份额独立与资方对账、清算、核销。用户视角的还款按冲抵顺序先在聚合层分配，再按比例下推到份额层——**任何一层对不齐都是对账差异**，所以总分核对（借据聚合 vs 份额汇总）是联合贷的日终必跑项，与账务的总分核对（见[账务系统设计-复式记账与日切](账务系统设计-复式记账与日切.md)）同构。

一笔联合贷的份额拆分与清分示例（我方 30% + 资方甲 50% + 资方乙 20%，支用 10000，还款 10300）：

```
支用 10000 ──拆分──▶ 我方份额 3000 / 甲 5000 / 乙 2000   (各自立子借据,各自计息)
还款 10300 ──冲抵──▶ 利息 300 / 本金 10000 (聚合层按冲抵顺序分配)
         ──下推──▶ 我方 3090 / 甲 5150 / 乙 2060        (按份额比例)
         ──清算──▶ 甲清算指令 5150 / 乙清算指令 2060 / 我方自营收入 3090 + 技术服务费
         ──校验──▶ Σ子借据应还 == 聚合借据应还 == 账务冲抵发生额   (三分核对)
```

任何一笔还款在聚合层、份额层、账务层各留一次记录，三层金额必须逐日轧平——联合贷的复杂度不是"会算比例"，而是**三层记录在部分成功、跨日、逾期、提前还款时仍然对得平**。

追问链
====

**Q1：资方对账文件没到，当日清算做不做？**
不做资金动作，只做记账隔离：待清分余额继续挂在内部户（它本来就在），清算指令顺延；对账文件恢复后先勾对再触发清算。反过来"照我方数据先清了再说"的风险是：资方侧某笔还款入账失败（扣款成功但资方记为冲正），按错数据清出真金白银就收不回来了。

**Q2：联合贷一边资方确认放款、另一边失败，钱怎么算？**
原子性协议 + 状态机：两边份额都到 READY 才触发统一放款指令；一方失败则另一方按合同约定回滚（冲正放款）或挂起人工处理（金额大时人工确认优先，自动回滚可能造成资方头寸操作成本）。跨机构不存在分布式事务（谁也做不了别人的 TM），只有**状态机 + 补偿 + 对账**三件套——这正是[分布式事务解决方案（总纲）](../../C-架构/分布式系统/理论基础/分布式事务解决方案.md)里 Saga/最终一致在机构间的现实形态。

**Q3：备付金户为什么用"应付—资方款"科目而不是自有资金科目？**
因为清分前的钱不归我方。科目错了，报表上平台自有资金虚增，内部户余额巡检（备付金 = Σ在途+待清分+挂账）也会失真——科目是资金归属的法律表达，不是记账便利问题。

**Q4：助贷方为什么还要建账务系统，资方不是有账吗？**
三个不可替代：**运营视角**（催收策略、额度管理要看我方口径的全量数据，不能逐家查资方）、**多资方中立**（借据在多家资方间流转/转让，业务连续性不能绑在某一家账务上）、**勾对锚点**（我方账务是三方对账的中间参照系，没有它资方之间无法互证）。我方账务不需要替代资方账，只需要"能对上"。

小结
====

* 资金流与信息流分离：指令与回执成对、信息流以账务为锚、资金指令幂等；
* 内部户/备付金是资金候车厅，余额构成等式（在途+待清分+挂账）本身就是核对项，不可挪用是红线；
* 资方对接以文件批次为主：加密签名、三方勾对、文件异常兜底、差异累积可见；
* 助贷单借据单资方，联合贷子借据按份额拆分再聚合，总分核对日终必跑；跨机构一致性只有状态机+补偿+对账三件套。
